# Звіт про прогрес конструювання та реалізації прототипу (Progress Report)

## 1. Загальний огляд та архітектурне позиціонування

У межах Лабораторної роботи 5 розпочато фазу конструювання основного прототипу системи **Baraholka NaUKMA** відповідно до архітектурних рішень, ухвалених у Лабораторній роботі 3 ([ADR-001](../architecture/decisions/ADR-001-architectural-style.md), [ADR-002](../architecture/decisions/ADR-002-database-storage.md), [ADR-003](../architecture/decisions/ADR-003-auth-mechanism.md)), та специфікації API з Лабораторної роботи 4.

Головним фокусом на цьому етапі стало подолання недоліків попередньої версії (де бізнес-логіка та тестові списки знаходилися безпосередньо всередині FastAPI-роутерів) і перехід до **тришарової чистої архітектури (Clean / Layered Architecture)**. Це забезпечило чітку межу між бізнес-логікою та веб-фреймворком (один із ключових критеріїв оцінки конструювання ПЗ).

- **Відповідальна роль:** Керівник прототипу (Prototype Lead) — Даніїл Чернявський (@megatr4n).
- **Аналізована гілка та стан:** Сформовано базовий каркас застосунку, повністю реалізовано доменний та сервісний шари першого ключового компонента системи — **Сервісу оголошень (Listing Service)**.

## 2. Базова структура коду проєкту

Кодова база в каталозі `src/` розділена на ізольовані шари з односпрямованими залежностями:

```
src/
├── domain/                  # 1. Доменний шар (чисті сутності та бізнес-правила)
│   ├── __init__.py
│   ├── listings.py          # Сутність Listing, статуси ListingStatus, Seed-дані
│   └── exceptions.py        # Доменні винятки (ListingNotFoundError, ListingForbiddenError тощо)
├── repositories/            # 2. Шар доступу до даних (Data Access / Repository Pattern)
│   ├── __init__.py
│   └── listings.py          # Інтерфейс ListingRepository (Protocol) та InMemoryListingRepository
├── services/                # 3. Сервісний шар (Use Cases / Бізнес-логіка)
│   ├── __init__.py
│   └── listings.py          # ListingService: фільтрація, пошук, пагінація, перевірка прав
└── api/                     # 4. Шар представлення (FastAPI HTTP-адаптер)
    ├── __init__.py
    ├── main.py              # Точка входу FastAPI, CORS, версіонування /api/v1
    ├── deps.py              # Інверсія залежностей (Dependency Injection) для сервісів
    ├── routers/
    │   ├── __init__.py
    │   └── listings.py      # HTTP-контролер: валідація, виклик сервісу, мапінг помилок
    └── schemas/
        ├── __init__.py
        └── listings.py      # Pydantic v2 моделі входу/виходу (розділення публічних і приватних даних)
```

### Принципи побудови шарів:

1. **`src/domain/` (Enterprise Business Rules):**
   - Сутність `Listing` реалізована як чистий Python dataclass без залежностей від FastAPI, Pydantic чи сторонніх бібліотек.
   - Метод `is_public()` централізує правило видимості товару покупцями (відображаються лише оголошення зі статусом `ACTIVE`).
   - Визначено доменні винятки (`ListingError`, `ListingNotFoundError`, `ListingUnauthorizedError`, `ListingForbiddenError`), які сигналізують про порушення інваріантів бізнес-логіки.

2. **`src/repositories/` (Data Access Interface):**
   - Використано інтерфейс `ListingRepository` на базі `typing.Protocol` (структурна типізація). Сервіси залежать виключно від абстрактного контракту сховища.
   - Реалізовано `InMemoryListingRepository` для функціонування прототипу до повної інтеграції PostgreSQL/SQLAlchemy. Завдяки патерну Repository підключення БД у Лабораторній 6 не вимагатиме жодних змін у сервісному або доменному шарах.

3. **`src/services/` (Application Business Rules):**
   - `ListingService` реалізує прикладні сценарії (Use Cases): отримання каталогу з фільтрацією та сортуванням, пошук за ключовими словами, створення оголошення від імені авторизованого користувача, редагування та видалення.
   - Сервіс не знає про HTTP-запити, статус-коди чи заголовки — він оперує доменними сутностями та типами Python.

4. **`src/api/` (Interface Adapters):**
   - Роутер виступає тонким контролером: приймає запит, валідує параметри через Pydantic-схеми, витягує ідентифікатор користувача (`ActorId`), викликає методи `ListingService` та конвертує доменні винятки у відповідні HTTP статус-коди (401, 403, 404).

## 3. Перший реалізований робочий компонент: Listing Service

Як перший працюючий компонент системи реалізовано **Каталог та управління життєвим циклом оголошень (Listing Management Component)**.

### Реалізований функціонал:
- **Публічний каталог (FR-006, FR-007, FR-008):** отримання списку активних оголошень із підтримкою пагінації (`skip`, `limit`), фільтрацією за категорією (`category_id`), діапазоном цін (`min_price`, `max_price`) та повнотекстовим регістронезалежним пошуком за назвою та описом (`query`). Зняті з публікації або заблоковані товари (`WITHDRAWN`) автоматично відфільтровуються.
- **Захист персональних даних продавців (SEC-002, TM-05):** у публічному каталозі та публічному перегляді оголошення поле `contact` (Telegram/email) фізично відкидається на рівні сервісу та серіалізатора `ListingPublicResponse`.
- **Створення оголошення (FR-002):** створення нового товару від імені поточного користувача. Сервер відкидає підробку `user_id` із тіла запиту і використовує ідентифікатор актора.
- **Контроль доступу та м'яке видалення (FR-003, FR-004, TM-02, SA-02):** оновлення (`PATCH`) та зняття з публікації (`DELETE` / soft delete) дозволені лише фактичному автору оголошення (`listing.user_id == actor_id`). Згідно з вимогою FR-004, видалення переводить оголошення у статус `WITHDRAWN` зі збереженням запису в історії продавця, виключаючи його з публічного каталогу.
- **Сувора валідація часткового оновлення:** схема `ListingUpdate` забороняє передачу явного `null` у полях, сигналізуючи `422 Unprocessable Entity`.

| Зауваження | Рішення команди | Стан |
|---|---|---|
| У роутері повторювався пошук оголошення циклом по `MOCK_LISTINGS` | Доступ до даних винесено в `InMemoryListingRepository`, а єдину перевірку наявності — у `ListingService._require_listing()` | Виправлено |
| Бізнес-логіка та робота зі сховищем знаходилися безпосередньо у FastAPI-роутері | Додано окремі доменний, репозиторний і сервісний шари; роутер залишено HTTP-адаптером | Виправлено |
| У `main.py` була тимчасова примітка для Backend Lead | Примітку видалено; у коді залишено лише технічну документацію та docstrings | Виправлено |
| `PATCH` і `DELETE` не перевіряли користувача та власника оголошення | Користувач визначається серверною сесією Entra ID (`require_current_user` → `CurrentUser`), власник перевіряється в `ListingService._require_owned`; `401`/`403` покрито регресійними тестами | Виправлено (31.10.2026) |
| `GET /listings` не повертає загальну кількість записів для посторінкової навігації | Поточний контракт зі списком збережено, щоб не ламати OpenAPI та клієнтів. Обгортку `total`/`items` буде погоджено з фронтендом перед зміною контракту | Відкладено |
| Listing endpoints ще використовують `X-Actor-Id` | Усі захищені маршрути (оголошення, обране, контакт, модерація) приймають лише `CurrentUser` із серверної сесії; запит лише з `X-Actor-Id` отримує `401` | Виправлено (31.10.2026) |

Зауваження щодо підтримуваності враховано в коді. Перевірку власника, яка на
Лаб 5 існувала лише на рівні прототипу, станом на 31.10.2026 закрито серверною
сесією Entra ID. Відкритим лишається лише контракт пагінації з `total`.

## 6. План розширення до Лабораторної роботи 6 (Мінімальний робочий прототип) — виконано

До наступної лабораторної роботи заплановано наступні інженерні кроки:
1. **Персистентність даних (ADR-002):** Реалізація класу `PostgresListingRepository` на базі SQLAlchemy 2.0 / asyncpg та налаштування міграцій структури бази даних через Alembic.
2. **Інтеграція автентифікації (ADR-003):** OIDC Authorization Code Flow, backend callback, перевірки MSAL, tenant/domain і server-side session реалізовані. Залишається додати exact redirect URI в Entra ID, вручну перевірити реальний tenant login і замінити `X-Actor-Id` у listing endpoints на `CurrentUser`.
3. **Модуль користувачів (`UserService`):** Додавання `User` з `tenant_id`, `entra_object_id`, перевіреним `@ukma.edu.ua`, локальною роллю та статусом блокування; без локального `password_hash`.
