## 2. Результати Bandit

**Знахідок: 0** (Low: 0, Medium: 0, High: 0).

**Інтерпретація.** Bandit шукає небезпечні шаблони коду: конкатенацію SQL (B608), виклики `subprocess` і `eval`, жорстко закодовані секрети, слабку криптографію. На поточному етапі API працює із заглушками в пам'яті, без БД, зовнішніх процесів і секретів, тож таких шаблонів у коді немає. Водночас Bandit не перевіряє логіку авторизації: хто і яке поле отримує у відповіді. Тому відповідно до завдання ми взяли загрозу з `docs/architecture/threat-model.md` і перевірили вручну, як код їй протистоїть.

## 3. Загроза TM-05: розкриття контакту продавця

**Загроза (STRIDE: I, серйозність висока).** Неавторизований відвідувач отримує `Listing.contact` через API, хоча інтерфейс приховує це поле. Пов'язані вимоги: SEC-002, US-006.

**Як код протистоїть.** Публічні `GET /api/v1/listings` і `GET /api/v1/listings/{listing_id}` оголошують `response_model=ListingPublicResponse`. Обробники повертають повний `ListingResponse`, але FastAPI серіалізує відповідь за `response_model` і відкидає поле `contact` на бекенді. Тобто захист виконується на сервері, а не прихованням у React, як і вимагає TM-05.

### Знахідка SA-01: витік контакту через PATCH

| | |
|---|---|
| **Що знайдено** | `PATCH /api/v1/listings/{listing_id}` мав `response_model=ListingResponse` і не вимагав автентифікації. Анонімний запит з порожнім тілом `{}` повертав `200` з повним оголошенням, включно з `"contact": "@student_ukma"`. Захист публічних GET обходився одним запитом. |
| **Чим знайдено** | Ручний аналіз `src/api/routers/listings.py` за моделлю загроз, підтверджено запитом через Swagger UI. Bandit знахідку не виявив (ID правила немає), бо це помилка логіки доступу, а не небезпечний виклик. |
| **Чому це ризик** | Порушує SEC-002 і TM-05: персональні контакти студентів доступні без входу, і їх можна масово зібрати, перебираючи ID оголошень. |
| **Що зроблено** | **Виправлено.** У `patch` замінено `response_model` на `ListingPublicResponse`. |
| **Pull request** | [#110](https://github.com/ukma-fin-ssdm-2026/Next-Gen/pull/110) |
| **Регресійний тест** | `tests/test_security.py::test_patch_listing_does_not_leak_contact` |

**Доказ регресійного тесту:**

- коміт `fa2dfd7`: тест додано до виправлення, результат `1 failed, 1 passed` (`PATCH` повертав `contact`);
- коміт `6f487f0`: виправлення, результат `2 passed`.

Другий тест, `test_get_listing_hides_contact`, фіксує наявний захист публічного GET, щоб він не зламався в майбутньому.

### Знахідка SA-02: зміна оголошення без автентифікації (свідомо прийнятий ризик)

| | |
|---|---|
| **Що знайдено** | `PATCH` і `DELETE` не перевіряють автентифікацію і власника оголошення. Під час перевірки SA-01 анонімний `PATCH` змінив `updated_at` запису. `POST` генерує `user_id` випадково (`uuid4()`), а не бере його з токена. |
| **Пов'язана загроза** | TM-02 (Tampering, серйозність висока). |
| **Чим знайдено** | Ручний аналіз і Swagger UI. |
| **Рішення** | **Свідомо прийнято** до реалізації автентифікації. Обґрунтування: модуль автентифікації (JWT, ADR-003) ще не реалізовано, API працює з тестовими даними в пам'яті без реальних користувачів, тож перевірити власника поки нема з чим. Ризик закривається разом з автентифікацією: визначати користувача з `sub` перевіреного JWT, перевіряти власника для `PATCH`/`DELETE` і покрити це негативними тестами (FR-003, FR-004), як вимагає TM-02. |
| **Стан на 31.10.2026** | **Закрито.** Усі змінні маршрути оголошень беруть користувача лише з серверної сесії (`require_current_user` → `CurrentUser`), а `ListingService._require_owned` порівнює власника; `X-Actor-Id` не приймається. Регресійні тести: `test_patch_foreign_listing_is_403`, `test_delete_foreign_listing_is_403_and_preserves_listing` у `tests/test_listings_api.py`. |

## 4. Бонус: Pre-commit хуки та пошук секретів (detect-secrets)

Для запобігання потраплянню невідформатованого коду, помилок лінтера та конфіденційних даних (API-ключів, паролів, токенів) у репозиторій налаштовано конфігурацію `.pre-commit-config.yaml` із чотирма автоматичними перевірками:

1. **Black:** перевірка форматування Python-коду за стандартом 88 символів.
2. **Flake8:** перевірка дотримання правил стилю PEP 8 (іменування, відступи, відсутність невикористаних імпортів).
3. **Bandit:** автоматичний аналіз безпеки AST-дерева на предмет відомих вразливих патернів коду.
4. **Detect-secrets (Yelp):** сканування кодової бази на наявність витоку секретів за базовим знімком `.secrets.baseline`.

## 5. Бонус: Аудит залежностей (SCA — Software Composition Analysis)

Для моніторингу вразливостей сторонніх компонентів у ланцюжку постачання (Supply Chain Security) впроваджено два інструменти:

1. **GitHub Dependabot (`.github/dependabot.yml`):**
   - Щотижневе автоматичне сканування маніфестів `pip` (Python) та `github-actions`.
   - Автоматичне створення Pull Request у разі виявлення CVE у бібліотеках.
2. **pip-audit у CI-конвеєрі (`.github/workflows/ci.yml`):**
   - Перевірка встановлених пакетів з `requirements.txt` проти офіційної бази вразливостей Python Packaging Advisory Database (PyPA) та OSV:
   ```bash
   pip-audit -r requirements.txt
   ```

### Результат аудиту:

```text
$ pip-audit -r requirements.txt
No known vulnerabilities found
```

Усі виробничі залежності проєкту (`fastapi`, `pydantic`, `uvicorn`, `pyyaml`, `httpx`) не містять відомих уразливостей.

### Опрацювання знахідки Dependabot

Dependabot виявив доступне оновлення інструмента аналізу безпеки **Bandit**
з версії `1.8.6` до `1.9.4`. Команда вирішила прийняти оновлення через
[PR #137](https://github.com/ukma-fin-ssdm-2026/Next-Gen/pull/137), оскільки
воно підтримує актуальність безпекового аналізатора та узгоджує залежність із
версією, використаною для локального аналізу.

На гілці PR автоматичний CI успішно виконав форматування, лінтинг, Bandit,
`pip-audit`, тести та перевірку актуальності OpenAPI. Відомої CVE у Bandit
`1.8.6` не зафіксовано: знахідка стосується доступного оновлення залежності, а
не підтвердженої вразливості. Рішення команди — оновити залежність, а не
приймати застарілу версію.

## 7. Висновки

- На Лаб 5 Bandit знахідок не дав, що очікувано для тодішніх заглушок без БД і секретів; на коді 31.10.2026 — 0 знахідок у профілі CI і одна Low (SA-03) у повному профілі. Його інтегровано в CI та pre-commit для постійного моніторингу.
- Ручна перевірка за моделлю загроз виявила реальну вразливість (SA-01), яку статичний аналізатор пропускає. Її виправлено з регресійним тестом.
- Впроваджено пре-комміт сканування секретів (`detect-secrets`) та регулярний аудит залежностей (`pip-audit`, Dependabot).
- Опрацьовано знахідку Dependabot щодо Bandit: прийнято оновлення `1.8.6` → `1.9.4` у PR #137 після успішного проходження CI.
- SA-02 / TM-02 закрито: замість прототипного `X-Actor-Id` користувач визначається серверною сесією Entra ID, власник перевіряється в сервісному шарі, сценарії покрито регресійними тестами.
