# Розподіл реалізації між учасниками

Код розподіляється вертикальними функціональними блоками. Власник блоку відповідає за його доменну модель, репозиторії, сервіси, API, тести та документацію.

## Функціональні блоки

| Учасник | Функціональний блок | Основний обсяг | Вимоги |
|---|---|---|---|
| **Артем Солодкий** | Автентифікація, користувачі та Frontend Lead | Microsoft Entra ID / OIDC, локальний `User`, перевірка `@ukma.edu.ua`, `CurrentUser`, сесія або JWT, ролі й блокування користувачів, а також мінімальний React UI та його інтеграція з API | `FR-001`, `FR-006`–`FR-008`, `FR-013`, `FR-014`, `SEC-001` |
| **Данііл Чернявський** | PostgreSQL і доступ до даних | SQLAlchemy, Alembic, транзакції, PostgreSQL-адаптери репозиторіїв, міграції та керування категоріями | `FR-012`, `REL-001` |
| **Євгеній Остапенко** | Повний життєвий цикл оголошення | Створення, редагування і зняття оголошення, фотографії через `ImageStorage`, стан товару та історія власних оголошень | `FR-002`–`FR-005` |
| **Богдан Солонина** | Функції покупця і контроль доступу | Обране, авторизований перегляд контакту продавця, адміністративне зняття оголошень та перевірка відповідних прав | `FR-009`–`FR-011`, `SEC-002` |

Пошук, каталог, фільтрація та сортування (`FR-006`–`FR-008`) уже мають базову реалізацію. Їх допрацьовує власник суміжної функції лише тоді, коли це потрібно для його сценарію.

## Межі відповідальності

Кожен функціональний блок включає:

- `src/domain/` — сутності, enum і бізнес-правила;
- `src/repositories/` — протоколи та адаптери сховищ;
- `src/services/` — сценарії використання;
- `src/api/schemas/` — схеми запитів і відповідей;
- `src/api/routers/` — endpoints;
- `tests/` — модульні та API-тести;
- `docs/api/` — OpenAPI й опис контракту.

Власник тест-кейсу `TP-*` у `docs/validation/test-plan.md` пише, запускає або демонструє відповідний тест для Лабораторної 7. Це не змінює власника функціонального блоку коду. Наприклад, Артем відповідає за `TP-001` і `TP-002`, але реалізація `FR-002` належить Євгенію.

## Спільні контракти

Перед інтеграцією команда погоджує:

- `CurrentUser` / `Actor` і спосіб передавання перевіреної ідентичності;
- `UserRepository`, `ListingRepository` і `FavoriteRepository`;
- `ImageStorage`;
- формат сесії або JWT та ролі;
- основні DTO, статус-коди й формат помилок.

Євгеній і Богдан можуть працювати через протоколи та in-memory адаптери, не очікуючи PostgreSQL. Тимчасовий `X-Actor-Id` не є production-автентифікацією: після готовності блоку Артема захищені endpoints мають використовувати перевірений `CurrentUser`.

## Організація роботи

Для кожного блоку створюється окремий Issue і гілка:

- `feature/auth-users` — Артем;
- `feature/postgres-persistence` — Данііл;
- `feature/listing-lifecycle` — Євгеній;
- `feature/buyer-access` — Богдан.

Великі зміни бажано ділити на невеликі PR:

1. доменні моделі та інтерфейси;
2. сервіс і модульні тести;
3. API та інтеграційні тести;
4. OpenAPI і документація.

## Рецензування

| Автор / блок | Основний рецензент |
|---|---|
| Артем — auth/users | Богдан — безпека, контакти та права доступу |
| Богдан — buyer/access | Артем — автентифікація й авторизація |
| Данііл — persistence/categories | Євгеній — інтеграція оголошень і фотографій |
| Євгеній — listing lifecycle | Данііл — репозиторії, транзакції та міграції |

Богдан як Integration Lead перевіряє спільну інтеграцію, а Данііл контролює CI та міграції. Автор не зливає власний PR без огляду іншого учасника.

## Definition of Done

- є позитивні, негативні та граничні тести;
- авторизація перевіряється на backend;
- OpenAPI згенеровано з актуального коду;
- документація відповідає реалізації;
- додано нотатку про використання ШІ;
- PR має опис, пов'язаний Issue та огляд іншого учасника;
- виконано:

```bash
python scripts/generate_openapi.py
git diff --exit-code -- docs/api/openapi-generated.yaml
python -m pytest -q
git diff --check
```
