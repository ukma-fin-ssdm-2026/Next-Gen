# План тестування — Baraholka NaUKMA

**Обсяг:** тестуємо реалізоване ядро оголошень: створення (включно з фотографіями через `ImageStorage` та станом товару `condition`), редагування власного оголошення, історію власних оголошень продавця (`ACTIVE` і `WITHDRAWN`), публічний каталог із текстовим пошуком і фільтрацією, зняття з публікації та нерозкриття контактів анонімним користувачам. Окремо тестуємо Microsoft Entra ID / OIDC adapter, login/callback, локального `User`, одноразовий `state`, server-side session і logout. Для PERF-001 плануємо окрему системну перевірку API каталогу. Свідомо не тестуємо ще не реалізовані обране, адміністрування, React UI, реальну PostgreSQL та відновлення після збою. Повну перевірку PERF-001 разом із React UI буде додано після появи клієнтського застосунку.

**Критерії виходу:** усі автоматизовані функціональні та security-кейси плану, крім `TP-N02`, проходять у CI; покриття `src/` не нижче 85%; немає відкритих критичних або високих дефектів; анонімні відповіді містять 0 контактних полів. `TP-N02` не входить до звичайного CI: його запускаємо окремо в контрольованому середовищі, а конфігурацію та результат фіксуємо у звіті тестування. До появи React UI успішний `TP-N02` підтверджує лише продуктивність API, а не повне виконання PERF-001 для сторінки.

**Ризики:** найбільший вплив мають обхід авторизації власника, витік контакту продавця, поява знятих оголошень у каталозі та деградація пошуку під навантаженням. OIDC/API-тести використовують fake MSAL client і in-memory user/session stores, тому не замінюють ручної перевірки реального tenant та не доводять роботу кількох backend-реплік. Listing endpoints тимчасово використовують `X-Actor-Id`, доки окремий інтеграційний крок не замінить його перевіреним `CurrentUser`. Також тести не доводять коректність PostgreSQL і зовнішнього хмарного сховища зображень; збереження фотографій за FR-002 наразі працює на рівні метаданих `image_urls`; позитивний авторизований доступ до контакту за FR-010 ще не реалізовано; повна перевірка PERF-001 заблокована до появи React UI.

### Перевірки Microsoft Entra ID

`TP-AUTH-01` і policy-level частина `TP-AUTH-02` реалізовані у `tests/test_auth_service.py`. MSAL adapter та перетворення криптографічно перевірених claims покриті `tests/test_entra_integration.py`; callback, збіг і одноразовість `state`, локальна сесія, блокування та logout — `tests/test_auth_api.py` і `tests/test_auth_sessions.py`. Перевірку signature та `nonce` делеговано MSAL `acquire_token_by_auth_code_flow`. Реальний вхід у tenant залишається ручною інтеграційною перевіркою після додавання exact redirect URI. `TP-AUTH-04` ще не виконано, доки listing endpoints приймають `X-Actor-Id`.

| № | Рівень | Сценарій | Очікуваний результат | Вимога |
|---|---|---|---|---|
| TP-AUTH-01 | Модульний | Валідні claims очікуваних issuer, audience, `tid`, `exp` та `@ukma.edu.ua` | Ідентичність прийнято і зв'язано з локальним `User` | FR-001 / SEC-001 |
| TP-AUTH-02 | Модульний, параметризований | Невірні signature, issuer, audience, `tid`, `exp` або domain | Вхід відхилено, `User` і сесію не створено | FR-001 / SEC-001 |
| TP-AUTH-03 | Інтеграційний | Callback з невірним або повторно використаним `state`/`nonce` | Callback відхилено без сесії | SEC-001 / TM-01 |
| TP-AUTH-04 | Інтеграційний API | Перевірений через Entra ID користувач намагається змінити чуже оголошення | `403`, дані не змінено | US-002 / FR-003, SEC-001, TM-02 |

## Бонуси

### Виконуваний нефункціональний security-тест — Бонус 0,25 бала

- **Власник:** Артем Солодкий.
- **Вимога:** `SEC-001` — backend відхиляє неприпустиму Entra-ідентичність до створення локального користувача.
- **Поріг:** 100% шести визначених policy-level негативних випадків мають завершуватися `InvalidIdentityError`, а локальний `User` не повинен створюватися.
- **Сценарії:** неправильні `tenant`, `issuer`, `audience`, завершений строк дії, домен поза `@ukma.edu.ua` та порожня локальна частина email.
- **Фактичний результат:** 6 із 6 випадків відхилено, тобто 100%; після кожної відмови репозиторій не містить користувача з переданою Entra-ідентичністю.
- **Межа перевірки:** тест отримує claims після передбаченої зовнішньої криптографічної перевірки. JWT signature, `state` і `nonce` цим тестом не перевіряються.

Команда запуску:

```bash
python -m pytest tests/test_auth_service.py::test_nfr_sec_01_invalid_claims_are_rejected -v
```
