# План тестування — Baraholka NaUKMA

**Обсяг:** тестуємо реалізоване ядро маркетплейсу оголошень:
1. Створення оголошень (включно з фотографіями через `ImageStorage` та станом товару `condition`, `FR-002`);
2. Редагування власного оголошення продавцем (`FR-003`);
3. Зняття оголошення з публікації зі збереженням даних в історії (`FR-004`);
4. Історію власних оголошень продавця (`ACTIVE` і `WITHDRAWN`, `FR-005`);
5. Публічний каталог із текстовим пошуком, фільтрацією та сортуванням (`FR-006`–`FR-008`);
6. Роботу покупця з "Обраним" (`FR-009`);
7. Захист конфіденційності контактів продавця для анонімних користувачів і контрольований доступ до контакту для автентифікованого покупця (`FR-010`, `SEC-002`);
8. Адміністративне зняття оголошення з обов'язковою причиною та журналом модерації (`FR-011`);
9. Керування та публічний перегляд категорій оголошень (`FR-012`): публічні ендпоінти перегляду та деталей, а також адміністративне додавання, перейменування та деактивація категорій із захистом за роллю `ADMIN` (`CurrentUser` із сесії);
10. Автентифікацію через Microsoft Entra ID / OIDC adapter, login/callback, перевірку `state`, створення сесій та logout (`FR-001`, `SEC-001`);
11. Виконуваний системний бенчмарк продуктивності API каталогу під конкурентним навантаженням (`PERF-001`, `TP-N02`).

Свідомо не тестуємо в цьому релізі: клієнтський React UI та процедури аварійного відновлення PostgreSQL кластера (`REL-001`).

**Критерії виходу:**
- Усі автоматизовані функціональні, регресійні, security-тести та OIDC-тести (`TP-001`–`TP-027`, `TP-N01`, `TP-N02`, `TP-AUTH-01`–`TP-AUTH-04`, `DT-01`–`DT-07`, AST-тести простежуваності) проходять успішно у CI;
- Виконуваний тест продуктивності `TP-N02` ([`tests/test_nfr_performance.py`](../../tests/test_nfr_performance.py)) демонструє час відгуку `p95 ≤ 300 мс` (фактично ~80.3 мс) під навантаженням 50 одночасних користувачів на 500 активних оголошеннях із 0% помилок;
- Покриття коду в `src/` не нижче 85%;
- Немає відкритих критичних або блокуючих дефектів (Critical/High);
- Публічні та анонімні відповіді містять рівно 0 контактних полів продавця (`SEC-002`).

**Ризики:** найбільший вплив мають обхід авторизації власника при модифікації чи видаленні, спроба модифікації структури категорій не-адміністратором, витік контактів продавця анонімним користувачам, деградація пошуку під конкурентним навантаженням та розсинхронізація матриці вимог і тест-плану. OIDC/API-тести використовують fake MSAL client і in-memory user/session stores; додатково 28.10.2026 вручну перевірено повний вхід через реальний tenant на розгорнутому HTTPS-стенді: login, callback, створення сесії, `/api/v1/auth/me` та redirect до Swagger UI працюють. Усі захищені listing endpoints використовують виключно `CurrentUser` (`require_current_user`) і відхиляють клієнтські заголовки `X-Actor-Id`.

### Перевірки Microsoft Entra ID

### Додатковий security-доказ виконуваного NFR-тесту

- **Власник:** Артем Солодкий.
- **Вимога:** `SEC-001` — backend відхиляє неприпустиму Entra-ідентичність до створення локального користувача.
- **Поріг:** 100% шести визначених policy-level негативних випадків мають завершуватися `InvalidIdentityError`, а локальний `User` не повинен створюватися.
