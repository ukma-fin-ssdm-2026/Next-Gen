# План тестування — Baraholka NaUKMA

**Обсяг:** тестуємо реалізоване ядро маркетплейсу оголошень:
1. Створення оголошень (включно з фотографіями через `ImageStorage`, станом товару `condition` та необов'язковою пропозицією нової категорії `suggested_category_name`, `FR-002`, `FR-015`);
2. Редагування власного оголошення продавцем (`FR-003`);
3. Зняття оголошення з публікації зі збереженням даних в історії (`FR-004`);
4. Історію власних оголошень продавця (`ACTIVE` і `WITHDRAWN`, `FR-005`);
5. Публічний каталог із текстовим пошуком, фільтрацією та сортуванням (`FR-006`–`FR-008`);
6. Роботу покупця з "Обраним" (`FR-009`);
7. Захист конфіденційності контактів продавця для анонімних користувачів і контрольований доступ до контакту для автентифікованого покупця (`FR-010`, `SEC-002`);
8. Адміністративне зняття оголошення з обов'язковою причиною та журналом модерації (`FR-011`);
9. Керування та публічний перегляд категорій оголошень (`FR-012`), а також пропозиції нових категорій продавцями і їх модерацію адміністратором (`FR-015` / `US-010`);
10. Автентифікацію через Microsoft Entra ID / OIDC adapter, login/callback, перевірку `state`, створення сесій та logout (`FR-001`, `SEC-001`);
11. Виконуваний системний бенчмарк продуктивності API каталогу під конкурентним навантаженням (`PERF-001`, `TP-N02`);
12. Вбудований приватний чат між користувачами зі сторінки оголошення, безпеку розмов (IDOR, блокування, відсутність витоку контактів), курсорну пагінацію, ліміти та коротке опитування polling (`FR-021`, `FR-022`, `SEC-003`, `PERF-002`, `TP-050`–`TP-056`).

Свідомо не тестуємо в цьому релізі: клієнтський React UI та процедури аварійного відновлення PostgreSQL кластера (`REL-001`).

**Критерії виходу:**
- Усі автоматизовані функціональні, регресійні, security-тести та OIDC-тести (`TP-001`–`TP-028`, `TP-N01`, `TP-AUTH-01`–`TP-AUTH-05`, `DT-01`–`DT-07`, AST-тести простежуваності) проходять успішно в обов'язковому CI;
- Виконуваний тест продуктивності `TP-N02` ([`tests/test_nfr_performance.py`](../../tests/test_nfr_performance.py)) в окремому workflow `Performance benchmark`, без coverage-інструментації, автоматично запускається для pull request у `main`: після трьох warm-up запитів виконує три незалежні раунди по 50 одночасних користувачів на 500 активних оголошеннях, вимагає 0% помилок і медіану round p95 `≤ 300 мс`;
- Покриття коду в `src/` не нижче 85%;
- Немає відкритих критичних або блокуючих дефектів (Critical/High);
- Публічні та анонімні відповіді містять рівно 0 контактних полів продавця (`SEC-002`).

**Ризики:** найбільший вплив мають обхід авторизації власника при модифікації чи видаленні, спроба модифікації структури категорій не-адміністратором, витік контактів продавця анонімним користувачам, деградація пошуку під конкурентним навантаженням та розсинхронізація матриці вимог і тест-плану. OIDC/API-тести використовують fake MSAL client і in-memory user/session stores; додатково 28.10.2026 вручну перевірено повний вхід через реальний tenant на розгорнутому HTTPS-стенді: login, callback, створення сесії, `/api/v1/auth/me` та redirect до Swagger UI працюють. Усі захищені listing endpoints використовують виключно `CurrentUser` (`require_current_user`) і відхиляють клієнтські заголовки `X-Actor-Id`.

  - **Серверний компонент (поточний автотест):** перевіряє ефективність бекенду та асинхронного ASGI-роутера у трьох незалежних раундах одночасної обробки 50 запитів через `httpx.AsyncClient` + `asyncio.gather` на базі з 500 оголошень без блокування потоків. Результат визначає медіана трьох round p95 при незмінному порозі 300 мс, що відкидає одиничний шум shared runner, але не маскує стійку деградацію.
  - **Наскрізний PERF-001 (Staging):** повне навантажувальне тестування з урахуванням мережевих затримок, транзакцій PostgreSQL, контейнеризації Docker та клієнтського рендерингу сторінки React заплановано виконувати за допомогою Locust/k6 проти розгорнутого стенду.

  - медіана round p95: **26,74 мс** (норматив вимоги: `<= 300 мс`);
  - `Max`: **49,87 мс**;
  - `Помилки`: 0.0% (150/150 успішних запитів);
  - `SEC-002`: підтверджено повне маскування контактів у всіх 150 відповідях;
  - 10 повторних локальних запусків виправленого benchmark дали однаковий результат `passed`.

У GitHub Actions цей часово чутливий бенчмарк автоматично запускається для pull request у `main` після кожного оновлення його гілки; за потреби доступний і ручний запуск через **Actions → Performance benchmark → Run workflow**.
