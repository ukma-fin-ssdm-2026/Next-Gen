# Веб-клієнт (React SPA)

Цей документ описує реалізований клієнт `frontend/`: як його запустити, які маршрути й
кінцеві точки API він використовує, як поводяться ключові екрани та що поки не реалізовано.
Вимоги й контракти API наведено в [requirements.md](../requirements/requirements.md) та
[api-design.md](../api/api-design.md); клієнт не є межею безпеки (див. [HLD](../architecture/high-level-design.md)).

## Стек і запуск

React 19, TypeScript, Vite, `react-router-dom`. Стилі лежать в одному файлі `src/styles.css`.

| Команда (у `frontend/`) | Призначення |
|---|---|
| `npm ci` | Встановлення залежностей |
| `npm run dev` | Dev-сервер `http://127.0.0.1:5173`; `/api`, `/uploads` і `/health` проксуються на `127.0.0.1:8000` |
| `npm run typecheck` | Перевірка типів (`tsc -b`) |
| `npm run build` | Перевірка типів і збірка в `frontend/dist` |

Якщо `frontend/dist` існує, FastAPI (`src/api/main.py`) віддає його з порту 8000. Після змін у клієнті
для цього режиму потрібно знову виконати `npm run build`.

## Структура

| Файл | Вміст |
|---|---|
| `src/App.tsx` | Маршрути, шапка, сторінки та їхні компоненти |
| `src/api.ts` | Усі HTTP-виклики до `/api/v1` (cookie-сесія, `credentials: "include"`) |
| `src/types.ts` | Типи відповідей і запитів API |
| `src/NaukmaLogo.tsx` | Логотип НаУКМА для футера |

## Маршрути

| Маршрут | Доступ | Екран |
|---|---|---|
| `/`  | Усі | Головна: швидкий пошук, лічильники, нещодавні оголошення |
| `/listings` | Усі | Каталог: пошук, категорія, діапазон ціни, сортування, посторінкова навігація |
| `/listings/:id` | Усі | Оголошення: галерея, ціна, опис, контакт продавця |
| `/listings/new` | Авторизовані | Створення оголошення |
| `/listings/:id/edit` | Власник | Редагування оголошення |
| `/my` | Авторизовані | Мої оголошення (активні та зняті, `FR-005`) |
| `/favorites` | Авторизовані | Обране |
| `/admin` | Адміністратор | Адмін-панель: блокування й розблокування користувача за email або ID з причиною (`FR-013`); черга пропозицій категорій зі схваленням (з можливістю виправити назву) і відхиленням із причиною (`FR-015`) |
| `/admin/complaints`, `/admin/feedback`, `/admin/blocked`, `/admin/logs/users`, `/admin/logs/admins` | Адміністратор | Вкладки адмін-панелі зі своїми адресами: скарги (`FR-016`), звернення (`FR-017`), заблоковані з причиною й розблокуванням (`FR-013`), журнали дій користувачів і адміністраторів із пошуком і фільтром за категорією; `?q=` і `?category=` зберігаються в адресі, тож посилання можна надсилати (`FR-018`) |
| `/feedback` | Авторизовані | Звернення до адміністрації: тема й повідомлення (`FR-017`); посилання в меню профілю й футері |
| `/profile` | Авторизовані | Профіль: ім'я, аватарка (з обрізанням у квадрат), контакти за замовчуванням (`FR-014`) |

## Використання API

| Дія клієнта | Запит |
|---|---|
| Поточний користувач | `GET /auth/me` |
| Профіль: ім'я, контакти | `PATCH /auth/me` |
| Аватарка | `PUT /auth/me/avatar` (`multipart/form-data`, поле `file`), `DELETE /auth/me/avatar` |
| Ім'я й аватарка продавця | `GET /users/{id}` (лише для авторизованих) |
| Категорії | `GET /categories` |
| Пропозиція нової категорії | `POST /listings` з `suggested_category_name` замість `category_id` (категорія «Інше» + заповнене поле «Своя категорія»; оголошення в «Інше» до розгляду) |
| Черга пропозицій (адміністратор) | `GET /category-suggestions?status=PENDING`, `POST /category-suggestions/{id}/approve` (необов'язкове `{name}`), `POST /category-suggestions/{id}/reject` (`{reason}`) |
| Каталог, оголошення | `GET /listings`, `GET /listings/{id}` |
| Мої оголошення | `GET /listings/my` |
| Завантаження фото | `POST /listings/images` (`multipart/form-data`, поле `files`) |
| Створення, зміна | `POST /listings`, `PATCH /listings/{id}` |
| Зняття з публікації | `DELETE /listings/{id}` (статус `WITHDRAWN`, запис зберігається) |
| Контакт продавця | `GET /listings/{id}/contact` |
| Обране | `GET /favorites`, `POST` і `DELETE /favorites/{id}` |
| Модерація (адміністратор) | `POST /admin/listings/{id}/withdraw` з причиною |
| Скарга на оголошення | `POST /listings/{id}/complaints` |
| Звернення до адміністрації | `POST /feedback` |
| Адмін: скарги, звернення | `GET /admin/complaints`, `POST /admin/complaints/{id}/resolve`, `GET /admin/feedback`, `POST /admin/feedback/{id}/resolve` |
| Адмін: журнали, заблоковані | `GET /admin/logs/users`, `GET /admin/logs/admins`, `GET /admin/users/blocked` |
| Вікно блокування | `GET /auth/blocked-status` (за сесією або квитком після входу) |
| Блокування користувача (адміністратор) | `POST /admin/users/{id}/block`, `/unblock` або `/admin/users/block-by-email`, `/unblock-by-email` з причиною |

## Поведінка екранів

### Сторінка оголошення (`FR-010`, `SEC-002`)

- Галерея з усіма фото: стрілки, лічильник, мініатюри, перемикання клавішами ← →.
- Авторизований користувач бачить контакт одразу: клієнт запитує `GET /listings/{id}/contact` при
  відкритті сторінки. Гість контакт не отримує, замість нього показано кнопку «Увійти, щоб побачити контакт».
- Власник замість «В обране» бачить «Редагувати оголошення» та «Зняти з публікації» (з підтвердженням).
- Адміністратор бачить додаткову кнопку модераційного зняття з обов'язковою причиною.

### Пропозиції категорій (`FR-015`)

- У формі створення оголошення після вибору категорії «Інше» з'являється необов'язкове поле «Своя категорія»
  (2–40 символів). Якщо його заповнено, у запит іде `suggested_category_name` замість `category_id`, оголошення
  публікується в «Інше», а після створення показується повідомлення, що категорію розгляне адміністратор.
  Якщо поле порожнє, оголошення просто потрапляє в «Інше» без пропозиції.
- Помилки бекенду (409 — така категорія чи пропозиція вже є; 429 — вже 3 пропозиції на розгляді; 422) показуються
  спливаючим повідомленням.
- Бейджа «категорія на розгляді» у «Моїх оголошеннях» немає: `GET /listings/my` не повертає `suggested_category_name`.
- На `/admin` адміністратор бачить чергу `PENDING` з кількістю оголошень: «Схвалити» (назву можна виправити) і
  «Відхилити» (причина від 5 символів). Після схвалення список категорій оновлюється.

### Скарги, звернення і вікно блокування (`FR-013`, `FR-016`, `FR-017`)

- На сторінці чужого оголошення авторизований користувач бачить «Поскаржитись на оголошення»: вікно з причиною й описом (для «Інше» опис обов'язковий). Гість бачить «Увійти, щоб поскаржитись».
- Заблокований користувач після входу (або при відповіді 403 на `/auth/me`) бачить модальне вікно з причиною й датою блокування та кнопкою «Зрозуміло, вийти».
- «Інше» у списку категорій форми оголошення має підказку «(або запропонуйте свою)».
- Стани оголошення: «Новий», «Як новий», «Задовільний», «З помітними дефектами», «На запчастини».
- На мобільному панель дій форм створення, редагування й профілю закріплена внизу екрана; кнопка «+» на цих сторінках ховається.

### Адмін-панель (`FR-013`)

- Пункт «Адмін-панель» у меню профілю й мобільному меню бачить лише `ADMIN`; сторінка `/admin` для інших
  показує «Немає доступу». Роль перевіряє бекенд, клієнт лише приховує інтерфейс.
- Форма приймає email `@ukma.edu.ua` (лише для тих, хто вже входив) або UUID користувача та причину (5–500 символів); кнопки «Заблокувати» й «Розблокувати».
  Результати виконаних у сесії дій показано списком; повний журнал — у вкладці «Журнал адмінів» (`/admin/logs/admins`).
- На сторінці чужого оголошення адміністратор бачить кнопку «Заблокувати продавця» з полем причини.
- Помилки бекенду (404, 409 — себе, адміністратор, уже в такому стані; 422) показуються спливаючим повідомленням.

### Профіль (`FR-014`)

- Сторінка `/profile`: зміна імені, аватарки та контактів за замовчуванням (Telegram/пошта, телефон, локація).
  Контакти пакуються в один рядок тим самим форматом, що й `contact` оголошення (див. нижче), ліміт 200 символів
  на клієнті (бекенд приймає до 300).
- Аватарка вибирається з файлу й обрізається у квадрат тим самим редактором, що й фото оголошень
  (результат 512×512 JPEG, сервер нормалізує до WebP). Її можна видалити; без неї показується ініціал.
- Аватарка відображається в шапці, мобільному меню, на сторінці профілю й у картці продавця на сторінці оголошення.
  Картка продавця для авторизованих завантажує ім'я й аватарку через `GET /users/{id}`; гість бачить загальний підпис.
- Форма створення оголошення автоматично підставляє контакти з профілю; їх можна змінити для конкретного
  оголошення. Редагування наявного оголошення використовує контакт самого оголошення, а не профілю.
- Зміна імені в профілі зберігається і не перезаписується при повторному вході через Microsoft.

### Створення й редагування (`FR-002`, `FR-003`)

- Фото: від 1 до 10, перше є обкладинкою, порядок можна змінювати. Файли йдуть на `POST /listings/images`,
  а в оголошення передаються повернуті адреси `image_url`.
- Обрізання: перед завантаженням фото відкривається вікно з кадром 4:3 (така сама пропорція, як у
  каталозі й на сторінці оголошення). Режими «Заповнити кадр» і «Вписати повністю», у другому порожні
  місця заповнюються полями (розмиття, світлі або темні). Результат до 1600 пікселів завширшки, JPEG.
  Уже завантажені фото можна переобрізати. Якщо браузер не може відкрити файл (наприклад, HEIC), його
  додано без змін.
- Опис необов'язковий. Категорію після публікації змінити не можна (її немає в `ListingUpdate`).
- Під час редагування контакт підтягується з `GET /listings/{id}/contact`.

### Контакт, телефон і локація

API має один рядок `contact` (3–200 символів). Щоб дозволити необов'язкові телефон і локацію без змін
бекенду, клієнт пакує їх у цей рядок окремими рядками:

```text
@student_ukma
Тел.: +380 50 123 45 67
Локація: Київ, Контрактова площа
```

Перший рядок є основним контактом (обов'язковий), інші два необов'язкові. Старі контакти з одним рядком
читаються без змін. Обмеження полів у формі: основний контакт до 100 символів, телефон до 20, локація до 60,
тому сума не перевищує 200. Телефон і локація мають ту саму класифікацію Personal Data, що й `contact`, і
віддаються лише через `GET /listings/{id}/contact`.

### Мої оголошення (`FR-004`, `FR-005`)

Вкладки «Активні» та «Знято» з лічильниками, статус кожного оголошення, дії «Редагувати» і «Зняти»
(зняте оголошення лишається в історії).

### Повідомлення

Успішні й помилкові повідомлення зникають самі через 4 секунди з плавним згасанням, їх також можна закрити вручну.

## Безпека

- Клієнт не передає `user_id`, роль чи власника як доказ особи: усе визначає серверна сесія.
- Приховування кнопок для гостя та перевірка «це моє оголошення» на клієнті лише покращують зручність.
  Авторизацію, перевірку власника й ролі `ADMIN` виконує бекенд.
- Контакт продавця не потрапляє в публічні відповіді та не кешується клієнтом поза станом сторінки.

## Обмеження та відкриті питання

| Тема | Стан |
|---|---|
| Адмін-панель | Реалізовано: блокування, черга пропозицій категорій, скарги, звернення, список заблокованих, журнали дій. Не реалізовано: `GET` для всіх категорій (у тому числі неактивних), список оголошень зі статусами, загальний список користувачів, «мої пропозиції» для автора, посилання на окрему скаргу чи звернення |
| Призначення адміністраторів | Лише через змінну `ADMIN_EMAILS` на сервері (див. README); інтерфейсу чи API для зміни ролі немає |
| Окремі поля `phone` і `location` | Тимчасово пакуються в `contact`; бажано перенести в API й схему даних |
| Автоматичні тести клієнта | Відсутні (клієнтський UI поза обсягом, див. [test-plan.md](../validation/test-plan.md)) |
