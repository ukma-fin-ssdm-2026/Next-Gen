# Модель загроз

## Обсяг і метод

Модель загроз охоплює вебсервіс Baraholka NaUKMA в межах поточного семестрового обсягу: React SPA, FastAPI backend, PostgreSQL і сховище фотографій оголошень. Оплата, доставка, вбудований чат, рейтинги та окремий мобільний застосунок не розглядаються, оскільки вони не входять до поточної версії продукту.

Аналіз виконано за методом STRIDE:

- **S — Spoofing:** підроблення особи;
- **T — Tampering:** несанкціонована зміна даних;
- **R — Repudiation:** заперечення виконаної дії;
- **I — Information Disclosure:** розкриття інформації;
- **D — Denial of Service:** відмова в обслуговуванні;
- **E — Elevation of Privilege:** підвищення привілеїв.

Основою аналізу є діаграма розгортання:

`docs/architecture/uml/deployment.puml`

## Архітектурний контекст

Система має клієнт-серверну трирівневу архітектуру:

1. React SPA виконується у веббраузері користувача.
2. FastAPI backend реалізований як модульний моноліт і надає REST API через HTTPS.
3. PostgreSQL зберігає структуровані дані, а окреме файлове або об'єктне сховище — фотографії оголошень. У PostgreSQL зберігаються URL або шляхи до них у сутності `ListingImage`.

Відповідно до ADR-003 зовнішнім постачальником ідентичності є Microsoft Entra ID НаУКМА. FastAPI обробляє OIDC Authorization Code callback, перевіряє `state`, `nonce`, підпис, `iss`, `aud`, `exp`, `tid` і домен `@ukma.edu.ua`, після чого зв'язує зовнішні `tenant_id` + `entra_object_id` з локальним `User`. Паролі Microsoft у системі не зберігаються. Локальні ролі, блокування і права на ресурси перевіряє backend.

Вибір конкретного хостингу та провайдера сховища ще не зроблено. `OQ-001` закрито вибором Microsoft Entra ID: для локального середовища зафіксовано redirect URI, а backend використовує непрозору server-side сесію. Production redirect URI та спільне сховище сесій визначаються разом із deployment.

## Активи, що потребують захисту

| Актив | Джерело в документації | Основна властивість захисту |
|---|---|---|
| Entra-ідентичність (`tenant_id`, `entra_object_id`) і локальний профіль | `User`, FR-001, SEC-001 | цілісність, автентичність |
| OIDC-токени, `client_secret`, `state`/`nonce` і локальна сесія | ADR-003 | конфіденційність, цілісність |
| Email, ім'я та контакт продавця | `User`, `Listing`, SEC-002 | конфіденційність |
| Оголошення, ціни, статуси й категорії | FR-002–FR-008, FR-012 | цілісність, доступність |
| Списки обраного | FR-009 | конфіденційність, цілісність |
| Фотографії оголошень | FR-002, `ListingImage` | цілісність, доступність |
| Ролі, блокування та модераційні рішення | FR-011–FR-013, `ModerationAction` | цілісність, підзвітність |

## Межі довіри

### TB-1 — Клієнтська зона ↔ серверна зона

React SPA працює на недовіреному пристрої. Усі параметри, ідентифікатори сутностей, файли, email, `user_id` і ролі вважаються недовіреними. Backend визначає поточного користувача лише з перевіреної сесії і виконує авторизацію кожного запиту.

### TB-2 — Серверна зона ↔ зона даних

FastAPI звертається до PostgreSQL і сховища фотографій. Доступ дозволяється лише серверному застосунку з мінімально необхідними привілеями. Облікові дані підключення не передаються клієнту й не зберігаються у вихідному коді.

### TB-3 — FastAPI ↔ Microsoft Entra ID

Entra ID є довіреним постачальником ідентичності, але backend не довіряє неперевіреним claims чи callback-параметрам. Обмін відбувається лише через HTTPS; metadata/JWKS отримуються з очікуваного issuer, а `client_secret` не передається браузеру.

## Шкала серйозності

- **Висока:** загроза може призвести до захоплення облікового запису, отримання прав адміністратора, витоку персональних даних, масової зміни або тривалої недоступності даних.
- **Середня:** вплив обмежений окремими записами чи короткочасним погіршенням роботи та потребує додаткових умов для реалізації.
- **Низька:** вплив незначний, легко виявляється та відновлюється без втрати важливих даних.

| TM-01 | TB-1/TB-3, OIDC callback та React SPA | S | Зловмисник повторно використовує callback, підміняє `state`/`nonce`, подає токен іншого tenant/audience або викрадає локальну сесію. | Висока | Перевіряти `state`, `nonce`, signature, `iss`, `aud`, `exp`, `tid` і `@ukma.edu.ua`; приймати authorization code лише один раз; застосовувати HTTPS, CSP і безпечні параметри локальної сесії. |
| TM-02 | TB-1, API оголошень та обраного | T | Автентифікований користувач підміняє `seller_id`, `user_id` або ID оголошення в запиті та редагує чуже оголошення, знімає його з публікації або змінює чужий список обраного. | Висока | Визначати поточного користувача лише з перевіреної сесії, зв'язаної з `tenant_id` + `entra_object_id`; для кожної операції перевіряти власника та статус; не приймати `seller_id`/`user_id` із клієнта; покрити FR-003, FR-004 і FR-009 негативними тестами. |
| TM-03 | TB-1, завантаження фотографій; сховище зображень | T | Замість дозволеної фотографії завантажується шкідливий, підроблений або надмірно великий файл; передане клієнтом ім'я файла використовується для перезапису іншого об'єкта. | Висока | На backend перевіряти фактичний тип, розмір і декодованість зображення; генерувати серверні ідентифікатори файлів; заборонити виконання завантаженого вмісту; зберігати файли поза web-root або в приватному bucket. Максимальний розмір, кількість і формати остаточно визначити в `OQ-002`. Аватарка (`PUT /auth/me/avatar`) проходить ту саму обробку: декодування, видалення метаданих, нормалізація до WebP, ліміт 10 МБ; замінений файл видаляється (`FR-014`, `TP-024`, `TP-025`). |
| TM-04 | FastAPI, `ModerationAction`, PostgreSQL | R | Адміністратор знімає оголошення або блокує користувача, а потім заперечує дію чи її причину. | Середня | Для кожної дії зберігати незмінний `ModerationAction` з `moderator_id`, цільовим `listing_id` або `target_user_id`, типом, причиною та часом; обмежити зміну журналу; синхронізувати зміну стану цілі та запис аудиту в одній транзакції. Це підтримує FR-011 і FR-013. |
| TM-05 | TB-1, API детальної сторінки оголошення | I | Неавторизований відвідувач отримує `Listing.contact` через API, хоча React приховує поле в інтерфейсі. | Висока | Формувати відповідь на backend відповідно до стану автентифікації та не включати контакт для анонімного запиту; не покладатися на приховування елемента в React; уникати персональних даних у URL і журналах; для приватних відповідей застосувати заборону спільного кешування. Перевірити автоматизованим тестом SEC-002/US-006. Контакти профілю (`User.contact`) повертаються лише власнику через `GET /auth/me`; публічний `GET /users/{id}` містить лише ім'я й аватарку (`FR-014`, `TP-025`). |
| TM-06 | TB-2, PostgreSQL і резервні копії | I | Через надмірні права БД, витік секрету або незахищену резервну копію розкриваються email, контакти та Entra-ідентифікатори. | Висока | Мінімальні права БД, захищені backup і з'єднання, секрети поза Git, відсутність токенів і персональних даних у журналах. |

| TM-12 | FastAPI, захищені API | E | Заблокований у Baraholka користувач продовжує діяти через чинну локальну сесію. | Висока | Перевіряти `User.is_blocked` для мутуючих і адміністративних дій, відкликати локальну сесію при блокуванні та обмежувати її строк дії. Реалізовано: `POST /admin/users/{id}/block` відкликає всі сесії користувача (`TP-026`, `TP-027`). |

## Перевірка покриття STRIDE

| Категорія | Загрози |
|---|---|
| Spoofing | TM-01 |
| Tampering | TM-02, TM-03, TM-10 |
| Repudiation | TM-04 |
| Information Disclosure | TM-05, TM-06, TM-11 |
| Denial of Service | TM-07, TM-08 |
| Elevation of Privilege | TM-09, TM-12 |

Модель містить ризики для обох меж довіри та всіх основних runtime-компонентів deployment-діаграми. Найвищий пріоритет мають серверна авторизація, захист контактних і облікових даних, безпечне завантаження фотографій та контроль адміністративних прав.

## Залишкові ризики й відкриті рішення

- `OQ-001` закрито вибором Microsoft Entra ID НаУКМА, локального exact redirect URI та непрозорої server-side сесії. OIDC callback і одноразовий `state` мають автоматизовані тести; реальний tenant login, production redirect URI та Redis-сховище сесій залишаються deployment-перевірками (TM-01).
- Формати, максимальний розмір і кількість фотографій потрібно визначити (`OQ-002`). До цього неможливо встановити остаточні ліміти для TM-03 і TM-08.
- Правила й перелік причин модерації потрібно узгодити (`OQ-003`). Технічний журнал `ModerationAction` уже передбачає збереження причини.
- Провайдер хостингу та сховища фотографій не обраний. Після вибору потрібно повторно перевірити мережеві правила, шифрування, резервне копіювання та керування секретами.
- Backend повторно читає локального користувача на кожному захищеному запиті й відкликає використану сесію після виявлення блокування. Блокування через API (`FR-013`) відкликає всі сесії користувача у process-local сховищі; для production залишається перенести session store у спільний (наприклад, Redis), щоб відкликання діяло на всі інстанси API (TM-12).
- До production-розгортання потрібно зафіксувати ротацію `client_secret`/сертифіката і реакцію на витік (TM-11).
