# Модель загроз

## Обсяг і метод

Модель загроз охоплює вебсервіс Baraholka NaUKMA в межах поточного семестрового обсягу: React SPA, FastAPI backend, PostgreSQL і сховище фотографій оголошень. Оплата, доставка, вбудований чат, рейтинги та окремий мобільний застосунок не розглядаються, оскільки вони не входять до поточної версії продукту.

Аналіз виконано за методом STRIDE:

- **S — Spoofing:** підроблення особи;
- **T — Tampering:** несанкціонована зміна даних;
- **R — Repudiation:** заперечення виконаної дії;
- **I — Information Disclosure:** розкриття інформації;
- **D — Denial of Service:** відмова в обслуговуванні;
- **E — Elevation of Privilege:** підвищення привілеїв.

Основою аналізу є діаграма розгортання:

`docs/architecture/uml/deployment.puml`

## Архітектурний контекст

Система має клієнт-серверну трирівневу архітектуру:

1. React SPA виконується у веббраузері користувача.
2. FastAPI backend реалізований як модульний моноліт і надає REST API через HTTPS.
3. PostgreSQL зберігає структуровані дані, а окреме файлове або об'єктне сховище — фотографії оголошень. У PostgreSQL зберігаються URL або шляхи до них у сутності `ListingImage`.

Вибір конкретного хостингу та провайдера сховища ще не зроблено. Спосіб підтвердження адреси `@ukma.edu.ua` також залишається відкритим питанням відповідно до `OQ-001` у вимогах, тому зовнішній поштовий сервіс не включено до поточної deployment-моделі.

## Активи, що потребують захисту

| Актив | Джерело в документації | Основна властивість захисту |
|---|---|---|
| Облікові дані та `password_hash` | `User`, FR-001, SEC-001 | конфіденційність, цілісність |
| Email, ім'я та контакт продавця | `User`, `Listing`, SEC-002 | конфіденційність |
| Оголошення, ціни, статуси й категорії | FR-002–FR-008, FR-012 | цілісність, доступність |
| Списки обраного | FR-009 | конфіденційність, цілісність |
| Фотографії оголошень | FR-002, `ListingImage` | цілісність, доступність |
| Ролі, блокування та модераційні рішення | FR-011–FR-013, `ModerationAction` | цілісність, підзвітність |

## Межі довіри

### TB-1 — Клієнтська зона ↔ серверна зона

React SPA працює на пристрої користувача, який не контролюється системою. Усі параметри HTTP-запиту, ідентифікатори сутностей, файли та значення ролей, отримані від клієнта, вважаються недовіреними. Перевірки лише в інтерфейсі не є засобом безпеки; backend повторно виконує автентифікацію, авторизацію та валідацію.

### TB-2 — Серверна зона ↔ зона даних

FastAPI звертається до PostgreSQL і сховища фотографій. Доступ дозволяється лише серверному застосунку з мінімально необхідними привілеями. Облікові дані підключення не передаються клієнту й не зберігаються у вихідному коді.

## Шкала серйозності

- **Висока:** загроза може призвести до захоплення облікового запису, отримання прав адміністратора, витоку персональних даних, масової зміни або тривалої недоступності даних.
- **Середня:** вплив обмежений окремими записами чи короткочасним погіршенням роботи та потребує додаткових умов для реалізації.
- **Низька:** вплив незначний, легко виявляється та відновлюється без втрати важливих даних.

## Реєстр загроз STRIDE

| ID | Компонент або межа | STRIDE | Сценарій загрози | Серйозність | Протидія або прийняття ризику |
|---|---|---|---|---|---|
| TM-01 | TB-1, endpoint автентифікації | S | Зловмисник перебирає паролі або використовує викрадену сесію, щоб видати себе за користувача з підтвердженим `@ukma.edu.ua` email. | Висока | Перевіряти підтвердження домену на backend; зберігати лише стійкий хеш пароля з унікальною сіллю; використовувати безпечні, обмежені за часом сесії; встановити `Secure`, `HttpOnly`, `SameSite` для cookie, якщо використовуються cookie; обмежувати частоту входів і не розкривати, чи існує email. Остаточний механізм підтвердження email узгодити в межах `OQ-001`. |
| TM-02 | TB-1, API оголошень та обраного | T | Авторизований користувач підміняє `seller_id`, `user_id` або ID оголошення в запиті та редагує чуже оголошення, знімає його з публікації або змінює чужий список обраного. | Висока | Визначати поточного користувача лише з перевіреної серверної сесії; для кожної операції перевіряти власника ресурсу та його статус; не приймати `seller_id`/`user_id` як авторитетне значення клієнта; покрити перевірки негативними тестами для FR-003, FR-004 і FR-009. |
| TM-03 | TB-1, завантаження фотографій; сховище зображень | T | Замість дозволеної фотографії завантажується шкідливий, підроблений або надмірно великий файл; передане клієнтом ім'я файла використовується для перезапису іншого об'єкта. | Висока | На backend перевіряти фактичний тип, розмір і декодованість зображення; генерувати серверні ідентифікатори файлів; заборонити виконання завантаженого вмісту; зберігати файли поза web-root або в приватному bucket. Максимальний розмір, кількість і формати остаточно визначити в `OQ-002`. |
| TM-04 | FastAPI, `ModerationAction`, PostgreSQL | R | Адміністратор знімає оголошення з публікації, а потім заперечує дію або її причину. | Середня | Для кожної дії зберігати незмінний запис `ModerationAction` з `moderator_id`, `listing_id`, типом, причиною та часом; не дозволяти звичайному користувачу змінювати журнал; синхронізувати зміну статусу оголошення і створення запису в одній транзакції. Це підтримує FR-011. |
| TM-05 | TB-1, API детальної сторінки оголошення | I | Неавторизований відвідувач отримує `Listing.contact` через API, хоча React приховує поле в інтерфейсі. | Висока | Формувати відповідь на backend відповідно до стану автентифікації та не включати контакт для анонімного запиту; не покладатися на приховування елемента в React; уникати персональних даних у URL і журналах; для приватних відповідей застосувати заборону спільного кешування. Перевірити автоматизованим тестом SEC-002/US-006. |
| TM-06 | TB-2, PostgreSQL і резервні копії | I | Через надмірні права облікового запису БД, витік секрету або незахищену резервну копію розкриваються email, контакти та хеші паролів. | Висока | Надати застосунку окремий обліковий запис БД з мінімальними правами; зберігати секрети в конфігурації середовища, а не в репозиторії; захистити мережеве з'єднання та резервні копії; обмежити доступ до backup; не записувати секрети й персональні поля в журнали. |

| TM-08 | TB-1, завантаження; сховище зображень | D | Користувач багаторазово завантажує великі файли та вичерпує дисковий простір, пропускну здатність або пам'ять backend. | Висока | Обмежити розмір, кількість і частоту завантажень; перевіряти `Content-Length`, але не довіряти лише йому; обробляти файли потоково; встановити квоти та очищати незавершені завантаження. Конкретні ліміти зафіксувати після закриття `OQ-002`. |
| TM-09 | TB-1, адміністративні API FastAPI | E | Звичайний користувач викликає endpoint модерації, керування категоріями або блокування і самостійно передає роль `ADMIN`. | Висока | На кожному адміністративному endpoint виконувати серверну role-based перевірку за `User.role`; ігнорувати роль із тіла запиту; за замовчуванням створювати `USER`; зміну ролей дозволяти лише через контрольований адміністративний процес; тестувати відмову для звичайного користувача за FR-011–FR-013. |
| TM-10 | TB-2, FastAPI ↔ PostgreSQL | T | Спеціально сформоване введення спричиняє SQL injection або некоректна конкурентна операція залишає оголошення й пов'язані записи в неузгодженому стані. | Висока | Використовувати параметризовані запити або ORM без конкатенації SQL; валідувати типи та діапазони; забезпечити PK, FK, `UNIQUE` і `NOT NULL`; критичні зміни виконувати транзакційно; відновлення перевіряти відповідно до REL-001 (RPO = 0, RTO ≤ 5 хв). |

## Перевірка покриття STRIDE

| Категорія | Загрози |
|---|---|
| Spoofing | TM-01 |
| Tampering | TM-02, TM-03, TM-10 |
| Repudiation | TM-04 |
| Information Disclosure | TM-05, TM-06 |
| Denial of Service | TM-07, TM-08 |
| Elevation of Privilege | TM-09 |

Модель містить ризики для обох меж довіри та всіх основних runtime-компонентів deployment-діаграми. Найвищий пріоритет мають серверна авторизація, захист контактних і облікових даних, безпечне завантаження фотографій та контроль адміністративних прав.

## Залишкові ризики й відкриті рішення

- Метод підтвердження адреси `@ukma.edu.ua` та відновлення доступу ще потрібно визначити (`OQ-001`). До цього TM-01 не можна вважати повністю опрацьованою.
- Формати, максимальний розмір і кількість фотографій потрібно визначити (`OQ-002`). До цього неможливо встановити остаточні ліміти для TM-03 і TM-08.
- Правила й перелік причин модерації потрібно узгодити (`OQ-003`). Технічний журнал `ModerationAction` уже передбачає збереження причини.
- Провайдер хостингу та сховища фотографій не обраний. Після вибору потрібно повторно перевірити мережеві правила, шифрування, резервне копіювання та керування секретами.
