# ADR-001: Вибір клієнт-серверного модульного моноліту

- **Статус:** Прийнято (Accepted)
- **Дата:** 2026-09-30
- **Пов'язані вимоги:** FR-001 - FR-013, NFR PERF-001, REL-001

## 1. Контекст та постановка проблеми

Для платформи студентського маркетплейсу «Baraholka NaUKMA» необхідно визначити базовий архітектурний стиль системи. На архітектурне рішення тиснуть такі вимоги та обмеження:
- **Функціональні вимоги (FR-001 - FR-013):** Забезпечення повного життєвого циклу оголошень (каталог, пошук, фільтрація, обране, контакти) та інструментів адміністрування для спільноти університету.
- **Продуктивність (NFR PERF-001):** Час відповіді системи на операції пошуку та фільтрації не повинен перевищувати 300 мс при навантаженні до 50 одночасних користувачів.
- **Надійність (NFR REL-001):** RPO = 0, RTO <= 5 хв у разі технічного збою.
- **Обмеження команди:** Невелика команда розробників (4 особи), семестрові часові рамки, необхідність швидкої доставки цінності без витрат на складну інфраструктуру.

## 2. Прийняте рішення

Використовувати клієнт-серверну архітектуру (Client-Server) з односторінковим клієнтом на React (SPA) та модульним монолітним бекендом на FastAPI із реляційною СУБД PostgreSQL.

## 3. Наслідки

### Плюси (позитивні наслідки):
- **Мінімальні затримки:** Взаємодія між бізнес-модулями (Auth, Listings, Moderation) відбувається через виклики функцій у пам'яті одного процесу, усуваючи мережеві витрати та гарантуючи виконання NFR PERF-001 (<= 300 мс).
- **Простота конвеєра та розгортання:** Бекенд збирається та розгортається як єдиний артефакт (Docker-контейнер), що не потребує оркестрації рівня Kubernetes чи складного моніторингу.
- **Транзакційна цілісність:** Гарантована підтримка ACID-транзакцій в єдиній базі даних без потреби у складних розподілених патернах (Saga, 2PC).
- **Чітке розмежування:** Фронтенд та бекенд повністю розділені через контракт REST API (JSON), що дозволяє паралельну розробку інтерфейсу та API.

### Застереження (на що звернути увагу):
- **Контроль зв'язності модулів:** Розробники мають суворо дотримуватися модульної структури (routers -> services -> repositories), щоб запобігти перетворенню кодової бази на заплутаний спагеті-моноліт.
- **Спільна точка відмови:** Падіння процесу FastAPI через критичну неперехоплену помилку зупиняє доступ до всіх функцій, тому в контейнері обов'язково має бути налаштований автоматичний перезапуск процесу (restart policy).

### Мінуси (компроміси та обмеження):
- **Неможливість гранулярного масштабування:** Каталог оголошень і кабінет модератора масштабуються лише разом як єдиний сервіс, навіть якщо навантаження на перегляд у рази перевищує створення оголошень.
- **Спільний релізний цикл:** Оновлення будь-якого одного ендпоінта вимагає повторного тестування та перерозгортання всього бекенду.

## 4. Розглянуті альтернативи та причини відхилення

### Альтернатива 1: Мікросервісна архітектура (окремі сервіси Auth, Listings, Moderation)
- **Причина відхилення:** Невиправдане ускладнення (overengineering) для масштабів одного університету. Додаткові накладні витрати на мережеві виклики між мікросервісами ставлять під загрозу ліміт затримки у 300 мс (NFR PERF-001). Вимагає складного DevOps-оточення (API Gateway, Service Discovery, distributed tracing), що неефективно витрачає обмежений час команди.

### Альтернатива 2: Моноліт із серверним рендерингом (Django / SSR з Jinja2)
- **Причина відхилення:** Серверний рендеринг погіршує швидкість реакції інтерфейсу при динамічній клієнтській фільтрації, пошуку та перемиканні фотографій (вимагає перезавантаження сторінки або надлишкових partial-перемальовок). Змішує логіку відображення із бізнес-правилами, обмежуючи паралельну роботу команди над UI та API.

### Альтернатива 3: Безсерверна архітектура (Serverless / AWS Lambda / Cloud Functions)
- **Причина відхилення:** Проблема холодного старту (cold start) функцій неприпустимо збільшує затримку першого запиту, що порушує NFR PERF-001. Крім того, створюється залежність від конкретного хмарного провайдера (vendor lock-in) та ускладнюється локальне тестування.
