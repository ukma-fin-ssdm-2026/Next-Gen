# ADR-003: Автентифікація через Microsoft Entra ID НаУКМА

- **Статус:** Прийнято; OIDC-адаптер і локальну сесію реалізовано, інтеграція listings триває
- **Початкова дата:** 2026-09-30
- **Пов'язані вимоги:** FR-001, FR-010, FR-011–FR-013, SEC-001, SEC-002

## 1. Контекст

Baraholka NaUKMA призначена для студентів і співробітників НаУКМА. Потрібно надійно підтвердити належність користувача до університету, не зберігати його пароль у проєкті та не довіряти ідентифікаторам, ролям чи email із запиту клієнта.

До 2026-10-23 ADR передбачав власні паролі, bcrypt і JWT, підписані застосунком. Це рішення замінено, оскільки команда зареєструвала застосунок безпосередньо в tenant **National University of Kyiv Mohyla Academy**.

## 2. Рішення

Використати Microsoft Entra ID як зовнішнього постачальника ідентичності за OpenID Connect / OAuth 2.0 Authorization Code Flow:

- реєстрація застосунку — **single-tenant** у tenant НаУКМА;
- платформа — **Web**, callback обробляє FastAPI;
- дозвіл Microsoft Graph — делегований `User.Read`; OIDC scopes — `openid`, `profile`, `email`;
- backend перевіряє `state`, `nonce`, підпис токена за ключами Entra ID, `iss`, `aud`, `exp`, `tid` та домен `@ukma.edu.ua`;
- локальний `User` прив'язується до пари `tenant_id` + `entra_object_id`, а не лише до email;
- роль `USER`/`ADMIN`, блокування та права на ресурси залишаються авторитетними в Baraholka і перевіряються backend;
- локальні паролі та `password_hash` не зберігаються.

Після callback backend створює непрозору server-side сесію. Cookie містить лише випадковий ідентифікатор, а Microsoft-токени залишаються на backend. Поточний in-memory адаптер підтримує один процес; перед горизонтальним масштабуванням він замінюється Redis-адаптером.

## 3. Поточний стан реєстрації

- Застосунок створено в tenant НаУКМА.
- Налаштовано `Microsoft Graph / User.Read` (делегований; admin consent за замовчуванням не потрібен).
- Backend очікує local redirect URI `http://localhost:8000/api/v1/auth/callback`; його ще треба додати як **Web** redirect URI в Entra ID. Production URI буде додано після вибору HTTPS-домену; URI має збігатися символ у символ.
- `client_id`, `tenant_id` і майбутній `client_secret` зберігаються лише в конфігурації середовища. Секрети не вносяться до Git або документації.

## 4. Наслідки

### Переваги

- підтвердження акаунта, MFA, політики входу і відновлення доступу делеговано НаУКМА;
- Baraholka не зберігає паролі і не реалізує власне відновлення пароля;
- tenant і домен перевіряються на backend.

### Компроміси та ризики

- Microsoft Entra ID та tenant НаУКМА стають зовнішньою залежністю для входу;
- помилка в `redirect_uri`, `client_id`, tenant або секреті заблокує вхід;
- потрібні окремі redirect URI для local, staging і production; у production — лише HTTPS;
- потрібні інтеграційні тести callback, `state`/`nonce`, tenant/domain і заблокованого локального користувача.

## 5. Розглянуті альтернативи

1. **Локальний email/password + bcrypt + власний JWT.** Відхилено: проєкт мав би самостійно захищати паролі, підтверджувати email і відновлювати доступ.
2. **Google Workspace OAuth 2.0.** Відхилено, оскільки команда має доступ до Microsoft Entra tenant НаУКМА.
3. **Багатотенантна Microsoft-реєстрація.** Відхилено: система призначена лише для НаУКМА, тому single-tenant має меншу поверхню помилкової конфігурації.
4. **HTTP Basic Authentication.** Відхилено через передавання облікових даних у кожному запиті та відсутність SSO/MFA.
