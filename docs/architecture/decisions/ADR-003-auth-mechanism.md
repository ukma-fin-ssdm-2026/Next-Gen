# ADR-003: Механізм автентифікації на основі stateless JWT-токенів

- **Статус:** Прийнято (Accepted)
- **Дата:** 2026-09-30
- **Пов'язані вимоги:** FR-001, FR-010, FR-011 - FR-013, NFR PERF-001, SEC-001, SEC-002

## 1. Контекст та постановка проблеми

Маркетплейс «Baraholka NaUKMA» призначений виключно для студентів та співробітників Києво-Могилянської академії. На механізм автентифікації та контролю доступу тиснуть такі вимоги:
- **Корпоративний доступ (FR-001):** Реєстрація дозволена лише за дійсною університетською поштою `@ukma.edu.ua`.
- **Захист контактів (FR-010, NFR SEC-002):** Контактні дані продавця (email, Telegram) повинні бути приховані від неавтентифікованих відвідувачів і відображатися лише зареєстрованим користувачам.
- **Рольовий контроль (FR-011 - FR-013):** Розмежування прав звичайних користувачів (`USER`) та адміністраторів (`ADMIN`) для модерації оголошень та блокування порушників.
- **Продуктивність (NFR PERF-001):** Перевірка прав не повинна сповільнювати час обробки HTTP-запитів.
- **Безпека облікових даних (NFR SEC-001):** Надійне збереження хешованих паролів із сіллю.

## 2. Прийняте рішення

Реалізувати автентифікацію на основі криптографічно підписаних stateless JWT-токенів у заголовку Authorization: Bearer, із серверною валідацією поштового домену @ukma.edu.ua та ролей користувача, а також хешуванням паролів алгоритмом bcrypt.

## 3. Наслідки

### Плюси (позитивні наслідки):
- **Stateless-перевірка автентичності токена:** Сервер FastAPI валідує криптографічний підпис JWT та термін дії локально за допомогою секретного ключа без попереднього звернення до PostgreSQL на етапі автентифікації запиту, що забезпечує швидку відмову для недійсних запитів у межах ліміту 300 мс (NFR PERF-001).
- **Захист від CSRF:** Використання HTTP-заголовка `Authorization: Bearer <token>` замість звичайних браузерних cookie за своєю природою усуває клас вразливостей Cross-Site Request Forgery.
- **Базовий контроль ролей у токені:** Поле `role` передається всередині підписаного payload токена, дозволяючи швидку первинну фільтрацію доступу в залежностях (dependencies) FastAPI для закриття адміністративних маршрутів (FR-011 - FR-013) без додаткового запиту щодо прав адміністратора.
- **Надійне хешування:** Збереження паролів у формі солених хешів bcrypt гарантує виконання NFR SEC-001 і захищає облікові дані при витоку дампу бази.

### Застереження (на що звернути увагу):
- **Короткий час життя токена:** Через неможливість легкого відкликання stateless-токенів термін дії Access Token має бути обмеженим (наприклад, 15-30 хвилин) із подальшим впровадженням механізму оновлення (Refresh Token).
- **Безпечне зберігання на клієнті:** React SPA має зберігати токен у пам'яті застосунку або безпечному сховищі браузера для мінімізації ризиків крадіжки через XSS.

### Мінуси (компроміси та обмеження):
- **Необхідність верифікації актуального статусу блокування в БД:** Оскільки stateless JWT не знає про блокування після видачі токена, для мутуючих операцій (як-от створення оголошення FR-002 / UC-001 або модерація) сервіс вимушений перевіряти статус активності користувача (`is_blocked`) безпосередньо в базі даних перед виконанням дії (відповідає TM-09 та діаграмі послідовності), щоб уникнути зловживань валідним токеном заблокованого акаунта (FR-013).

## 4. Розглянуті альтернативи та причини відхилення

### Альтернатива 1: Традиційні сесії на стороні сервера (Session Cookies + Redis або БД)
- **Причина відхилення:** Вимагає звернення до бази даних або налаштування окремого сервісу Redis під час кожного клієнтського запиту, що збільшує час відповіді та ускладнює інфраструктуру. Крім того, робота з куками між окремими доменами фронтенду та бекенду вимагає складного налаштування CORS, `SameSite` та CSRF-токенів.

### Альтернатива 2: Інтеграція Google Workspace OAuth 2.0 (SSO НаУКМА)
- **Причина відхилення:** Потребує офіційного схвалення, надання прав та реєстрації додатку в хмарній консолі Google адміністраторами НаУКМА, що не гарантується для навчального проєкту. Створює критичну зовнішню точку відмови для локальної розробки команди та автоматизованих тестів у GitHub Actions.

### Альтернатива 3: HTTP Basic Authentication
- **Причина відхилення:** Передача незашифрованого логіна та пароля у кожному HTTP-запиті несе критичні ризики безпеки у разі перехоплення трафіку; не підтримує обмеження сесій у часі та тонке керування ролями.
