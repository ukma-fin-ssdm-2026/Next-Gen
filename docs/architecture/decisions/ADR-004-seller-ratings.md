# ADR-004: Оцінки продавців (рейтинг зірками)

- **Статус:** Прийнято (Accepted); реалізація попереду
- **Дата:** 2026-11-10
- **Пов'язані вимоги (будуть внесені до `requirements.md` разом із кодом):** FR-019, FR-020, SEC-001, SEC-002; суміжні — FR-010, FR-013, FR-018
- **Пов'язані рішення:** ADR-002 (PostgreSQL), ADR-003 (автентифікація), ADR-005 (чат)

> Оцінки продавців входять в обсяг проєкту як повноцінна функція. Відповідно до `AGENTS.md` і `tests/test_traceability.py` вимоги, RTM, тест-план, діаграми й OpenAPI оновлюються **в тій самій гілці, що й код і тести**. До злиття `requirements.md` і `Project-Description.md` ще містять «рейтинги й відгуки про продавців» у переліку «поза межами».

## 1. Контекст

Покупець не має способу оцінити надійність продавця перед зустріччю. Оплата й передача товару відбуваються поза системою (C-002), тому репутація продавця є основним сигналом довіри. Усі користувачі автентифіковані через tenant НаУКМА (ADR-003), тобто кожен акаунт відповідає реальній особі університету, що суттєво ускладнює накрутки.

## 2. Рішення (погоджено з Артемом Солодким)

| № | Питання | Рішення |
|---|---|---|
| 1 | До чого прив'язана оцінка | До **продавця**; `listing_id` необов'язковий і лише дає контекст |
| 2 | Скільки оцінок на пару «автор — продавець» | **Одна**; автор може її змінити або видалити |
| 3 | Текст відгуку | **Лише зірки (1–5)**; текстові відгуки не входять до v1 |
| 4 | Модерація | **Після публікації**: оцінка видима одразу, адміністратор може приховати |
| 6 | Відповіді продавця | **Відкладено** |
| — | Захист від накруток | «Варіант 3»: без доказу взаємодії, але з обмеженнями (див. 2.4) |

### 2.1 Модель даних

Нова сутність `SellerReview` (таблиця `seller_reviews`, міграція Alembic `0005`):

| Атрибут | Тип | Обмеження | Опис |
|---|---|---|---|
| `review_id` | UUID | PK | Ідентифікатор оцінки |
| `seller_id` | UUID | FK → `User.user_id`, Required | Продавець, якого оцінено |
| `author_id` | UUID | FK → `User.user_id`, Required | Автор оцінки; береться лише з серверної сесії |
| `listing_id` | UUID | FK → `Listing.listing_id`, Nullable | Оголошення, у контексті якого поставлено оцінку |
| `rating` | smallint | CHECK 1–5, Required | Кількість зірок |
| `status` | enum | `VISIBLE` / `HIDDEN`, default `VISIBLE` | Стан модерації |
| `hidden_reason` | text | Nullable | Причина приховування (обов'язкова при `HIDDEN`) |
| `hidden_by` | UUID | FK → `User.user_id`, Nullable | Адміністратор |
| `hidden_at` | datetime | Nullable | Час приховування (UTC) |
| `created_at`, `updated_at` | datetime | Required | Час створення й останньої зміни (UTC) |

Обмеження: `UNIQUE (author_id, seller_id)`, `CHECK (author_id <> seller_id)`, індекс `(seller_id, status)`. Повторна оцінка тим самим автором виконує оновлення (upsert), а не створює дубль. Якщо згодом знадобляться текстові відгуки, додається nullable-колонка `comment` окремою міграцією.

### 2.2 API (усі шляхи під `/api/v1`)

| Метод і шлях | Доступ | Результат |
|---|---|---|
| `PUT /users/{seller_id}/review` `{rating, listing_id?}` | автентифікований | `201` створено, `200` оновлено; `403` себе/заблокований, `404` продавця немає, `422` невалідне значення, `429` ліміт |
| `DELETE /users/{seller_id}/review` | автор | `204`; `404`, якщо оцінки немає |
| `GET /users/{seller_id}/rating` | публічний | `{average, count, distribution}`; `my_rating` лише для автентифікованого |
| `GET /admin/reviews?seller_id=&author_id=` | адміністратор | Список для розгляду, з агрегатами по автору |
| `POST /admin/reviews/{review_id}/hide` `{reason}` та `/restore` | адміністратор | Приховує або повертає оцінку |

Ідентифікатор автора, роль і права завжди визначає сервер; клієнтські `author_id`/`user_id` ігноруються (TM-02). У відповіді деталей оголошення додається `seller_rating {average, count}`; для каталогу агрегати вибираються одним запитом на всі `seller_id` сторінки (без N+1).

### 2.3 Правила відображення

- Середнє показується від `REVIEW_MIN_COUNT_TO_DISPLAY` оцінок (початково **3**); менше показується лише кількість («Мало оцінок»). Це константа конфігурації.
- Оцінки зі статусом `HIDDEN` не входять у середнє й розподіл, але зберігаються для розгляду.
- Автори оцінок публічно **не показуються** (лише агрегат). Це знижує ризик помсти й узгоджується з FR-014 (приватність).

### 2.4 Захист від зловживань

- Лише акаунти tenant НаУКМА; один голос на пару; оцінка собі заборонена на рівні БД і сервісу.
- Ліміт зміни оцінок на автора (початково 10 на добу). Лічильник береться із журналу `ActivityEvent` (події `REVIEW_SET`, `REVIEW_REMOVED`), тож не потрібен окремий стан у пам'яті процесу.
- Адмін-панель показує автора з аномальною активністю (багато однозіркових оцінок за короткий час) і дозволяє приховати оцінку з причиною. Приховування й відновлення записуються в журнал дій адміністраторів через `ActivityEvent` (типи `REVIEW_HIDDEN`, `REVIEW_RESTORED`, FR-018) і зберігаються в самій оцінці (`hidden_by`, `hidden_reason`, `hidden_at`); `ModerationAction` не змінюється.
- Обмеження варіанта 3: оцінку може поставити той, хто ніколи не спілкувався з продавцем. За рішенням автора зв'язку оцінки з чатом (ADR-005) немає; можливе посилення потоком «продано» лишається відкритим питанням.

## 3. Наслідки

### Переваги
- Малий обсяг: одна таблиця, п'ять ендпоінтів, без нових зовнішніх залежностей.
- Модерація після публікації не гальмує користувачів, а журнал зберігає підзвітність.
- Незалежне від чату: можна реалізувати першим.

### Компроміси та ризики
- Без доказу взаємодії можливі скоординовані накрутки; ризик обмежується акаунтами НаУКМА, лімітами й ручним розглядом.
- Один голос на пару означає, що кілька угод з одним продавцем не враховуються окремо.
- Агрегат у каталозі додає запит на сторінку; індекс `(seller_id, status)` і пакетна вибірка утримують PERF-001.

## 4. Відкриті питання

1. Чи показувати «★ 4.8 (12)» на картках у каталозі, чи лише на сторінці оголошення? (пропозиція: на сторінці оголошення, у каталозі після перевірки PERF-001)
2. Чи потрібна публічна сторінка продавця для цього блоку, чи достатньо сторінки оголошення?
3. Чи ховати оцінки користувача автоматично, коли адміністратор його блокує (FR-013)?
4. Чи вводити пізніше текст відгуків, відповіді продавця й потік «продано» (рішення 3 і 6 відкладено)?

## 5. Розглянуті альтернативи

1. **Оцінка лише після угоди («продано»).** Найчесніше, але потребує нового потоку статусів і покупця; відкладено як наступний етап.
2. **Оцінка лише за наявності розмови (ADR-005).** Відхилено за рішенням автора: оцінки й чат лишаються незалежними функціями.
3. **Оцінка лише тим, хто відкривав контакт продавця.** Потребує журналу переглядів контактів, а факт перегляду слабко свідчить про угоду.
4. **Прив'язка до оголошення замість продавця.** Оцінки розпорошуються по знятих оголошеннях і не формують репутацію продавця.
5. **Текстові відгуки одразу.** Збільшують обсяг модерації та ризик ображання, тому відкладені.
