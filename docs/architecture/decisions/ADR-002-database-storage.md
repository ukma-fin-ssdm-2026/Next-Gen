# ADR-002: Вибір реляційної СУБД PostgreSQL та SQLAlchemy ORM

- **Статус:** Прийнято (Accepted)
- **Дата:** 2026-09-30
- **Пов'язані вимоги:** FR-001 - FR-013, NFR REL-001, SEC-001, SEC-002

## 1. Контекст та постановка проблеми

Маркетплейс «Baraholka NaUKMA» оперує пов'язаними сутностями: користувачі (`User`), оголошення (`Listing`), фотографії (`ListingImage`), обране (`Favorite`) та аудит дій адміністратора (`ModerationAction`). На вибір сховища даних тиснуть такі вимоги:
- **Цілісність зв'язків (FR-001 - FR-013):** Необхідно виключити появу «осиротілих» оголошень без дійсного автора або записів обраного для неіснуючих товарів.
- **Надійність транзакцій (NFR REL-001):** Гарантія нульової втрати підтверджених операцій (RPO = 0) та швидке відновлення (RTO <= 5 хв) у разі апаратного збою.
- **Безпека чутливих даних (NFR SEC-001, SEC-002):** Збереження Entra-ідентифікаторів без локальних паролів, обмеження доступу до персональних контактів продавця та захист від ін'єкцій.

## 2. Прийняте рішення

Використовувати реляційну СУБД PostgreSQL разом із SQLAlchemy ORM та інструментом міграцій Alembic для постійного зберігання всіх структурованих даних системи.

## 3. Наслідки

### Плюси (позитивні наслідки):
- **Суворий контроль цілісності:** Зовнішні ключі (Foreign Keys), обмеження `NOT NULL`, `UNIQUE` та каскадне видалення гарантують відсутність неузгоджених чи втрачених зв'язків на рівні рушія бази даних.
- **ACID-транзакційність:** Повна відповідність вимогам надійності NFR REL-001; створення оголошення разом із фотографіями або фіксація модерації виконуються атомарно.
- **Захист від SQL-ін'єкцій:** Рівень абстракції SQLAlchemy автоматично використовує параметризовані запити, мінімізуючи загрозу порушення цілісності TM-10 зі STRIDE-моделі.
- **Керована еволюція схеми:** Alembic дозволяє версіонувати кожну зміну структури БД у git та безперешкодно розгортати міграції на різних середовищах.

### Застереження (на що звернути увагу):
- **Оптимізація зв'язаних запитів:** При вибірці списку оголошень разом із фотографіями необхідно використовувати `joinedload` або `selectinload` в SQLAlchemy, щоб уникнути проблеми N+1 запитів і просідання часу відповіді.
- **Індексація фільтрів:** Для дотримання ліміту 300 мс (NFR PERF-001) критично додати індекси на поля `category_id`, `status`, `seller_id` та `created_at`.

### Мінуси (компроміси та обмеження):
- **Фіксована схема:** Будь-яке додавання нового поля чи зміна типу атрибута вимагає написання, перевірки та накатування міграції Alembic перед оновленням бекенду.
- **Споживання ресурсів:** PostgreSQL вимагає окремого контейнера та помітно більшого обсягу оперативної пам'яті для роботи буферів порівняно з легковаговими рішеннями на зразок SQLite.
- **Серіалізація конкурентних операцій:** In-memory реалізація репозиторіїв використовувала об'єктний `threading.Lock` для серіалізації операцій на кшталт перевірки ліміту оголошень або зміни статусу модерації. З переходом на PostgreSQL репозиторій створюється на кожен HTTP-запит (окрема SQLAlchemy-сесія), тому об'єктний лок більше не серіалізує конкурентні запити між процесами/подами. Для критичних операцій (наприклад, перевірка ліміту перед додаванням оголошення, атомарне зняття з публікації) необхідно використовувати `SELECT ... FOR UPDATE` або унікальні обмеження на рівні БД. **Поточний стан (MVP):** ризик гонки задокументовано; реалізація `SELECT ... FOR UPDATE` залишена на наступну ітерацію після виявлення реальних конфліктів у навантажувальних тестах.

## 4. Розглянуті альтернативи та причини відхилення

### Альтернатива 1: Документоорієнтована NoSQL СУБД MongoDB
- **Причина відхилення:** Відсутність суворої підтримки реляційних зв'язків і зовнішніх ключів на рівні рушія БД створює ризик неузгодженості даних (наприклад, дублювання контактів продавця або залишення недійсних посилань при видаленні користувача). Реалізація контролю цілісності вручну в коді застосунку суттєво ускладнює бекенд і порушує NFR REL-001.

### Альтернатива 2: Вбудована файлова СУБД SQLite
- **Причина відхилення:** Блокування всієї бази даних на рівні файлу під час запису (file-level locking) унеможливлює паралельну роботу багатьох користувачів одночасно. Крім того, існує значний ризик пошкодження файлу при несподіваній зупинці контейнера, що суперечить вимозі RPO = 0.

### Альтернатива 3: In-Memory сховище (Redis як основна база даних)
- **Причина відхилення:** Сховище ключ-значення в оперативній пам'яті не підходить для складної реляційної фільтрації за кількома критеріями одночасно (категорія, ціна, стан товару). Не гарантує довговічності даних без складного налаштування персистентності на диск, що порушує вимоги надійності.
