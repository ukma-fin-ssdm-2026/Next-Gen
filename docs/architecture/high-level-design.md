# Високорівнева архітектура (High-Level Design)

## Архітектурний стиль

Для проєкту "Baraholka NaUKMA" обрано **Клієнт-серверну архітектуру (Client-Server)** із бекендом у формі **Моноліту (Monolithic API)**.

### Обґрунтування вибору:
1. **Простота розробки та розгортання:** Оскільки застосунок має відносно невеликий і чітко окреслений набір функцій (дошка оголошень для одного університету), мікросервісний підхід створив би невиправдані накладні витрати (overengineering) на мережеву взаємодію, DevOps та управління транзакціями. Моноліт дозволяє швидко доставляти фічі силами невеликої команди.
2. **Чіткий поділ відповідальності:** Клієнтський застосунок (React SPA) відповідає виключно за рендеринг інтерфейсу і взаємодію з користувачем, тоді як сервер (FastAPI) концентрує всю бізнес-логіку, валідацію і безпеку.
3. **Ефективність:** Зв'язок між компонентами бекенду відбувається через виклики функцій у пам'яті (in-process), що є найшвидшим можливим способом взаємодії, на відміну від HTTP-запитів між мікросервісами.

## Основні компоненти та їхня взаємодія

Система складається з трьох фізичних рівнів (Tiers), які відображені на компонентній діаграмі:

1. **Клієнтська частина (Frontend)**
   - **React SPA:** Завантажується в браузер користувача, відображає UI та ініціює вхід через backend. Збирається у `frontend/dist` і віддається тим самим FastAPI-сервісом (SPA fallback у `src/api/main.py`), тож окремого вебсервера немає. Не містить `client_secret` і не вважається межею безпеки.

2. **Серверна частина (Backend - FastAPI Monolith)**
   - **API Router (REST):** Єдина точка входу для всіх HTTP-запитів. Відповідає за маршрутизацію запитів до відповідних контролерів.
   - **Auth Service:** Реалізує OIDC Authorization Code Flow з Microsoft Entra ID НаУКМА, обробляє callback, перевіряє claims і tenant/domain, зв'язує зовнішню ідентичність із локальним `User`. Паролі не приймає і не зберігає.
   - **Listing Service:** Керує логікою створення, редагування, фільтрації та пошуку оголошень.
   - **Favorite / Seller Contact Services:** Обране покупця і видача контакту продавця лише автентифікованому користувачу (FR-009, FR-010).
   - **Moderation Services:** Зняття оголошень, блокування й розблокування користувачів, рішення щодо пропозицій категорій; кожна така дія записується в незмінний журнал `ModerationAction` (FR-011–FR-013, FR-015).
   - **Complaint / Feedback / Activity Log Services:** Скарги на оголошення та звернення до адміністрації, їх розгляд; ці події та дії користувачів записуються окремим `ActivityLogService` у `ActivityEvent` і показуються в журналах дій користувачів і адміністраторів (FR-016–FR-018).
   - **ORM / Data Access Layer:** SQLAlchemy 2.x і репозиторії `src/repositories/postgres_*.py`; одна сесія БД на HTTP-запит (commit наприкінці, rollback при помилці), схема ведеться міграціями Alembic. Без `DATABASE_URL` використовуються in-memory репозиторії для локальної розробки й тестів.

3. **Сховище даних (Data Tier)**
   - **PostgreSQL Database:** Реляційна база даних, яка забезпечує ACID-властивості для надійного зберігання сутностей (`User`, `Listing`, `Favorite` тощо).
   - **Image Storage:** Локальне файлове сховище на Docker-томі `uploads_data` (`LocalImageStorage`, каталог `/var/lib/baraholka/uploads`). Фото нормалізуються у WebP, PostgreSQL зберігає лише ключі й метадані `ListingImage`, файли віддає FastAPI через `/uploads/{key}`. Інтерфейс `ImageStorage` дозволяє згодом замінити том на об'єктне сховище (S3) без змін у сервісах.

4. **Зовнішній постачальник ідентичності**
   - **Microsoft Entra ID НаУКМА:** single-tenant OIDC-провайдер, який підтверджує обліковий запис та видає підписані токени. Проєкт запитує лише `User.Read` і OIDC scopes, необхідні для входу.

## Інтерфейси між компонентами

- **React SPA ↔ FastAPI Server:** 
  - Протокол: `HTTP/HTTPS`.
  - Формат даних: `JSON` по REST (або `multipart/form-data` для завантаження фото).
  - Безпека: непрозора серверна сесія — випадковий токен у cookie `baraholka_session` (`HttpOnly`, `SameSite=Lax`, `Secure` вмикається змінною `SESSION_COOKIE_SECURE`), зв'язок токена з `User` зберігається на сервері (in-memory, TTL 8 год). Клієнт не передає власний `user_id` як доказ особи.
- **FastAPI Auth Service ↔ Microsoft Entra ID:**
  - Протокол: OpenID Connect / OAuth 2.0 Authorization Code Flow через HTTPS.
  - Секрети: `client_secret` і redirect URI зберігаються в конфігурації середовища, а не у frontend чи Git.
- **FastAPI Server ↔ PostgreSQL Database:**
  - Протокол: `TCP/IP` (PostgreSQL Wire Protocol) у внутрішній Docker-мережі `internal`; порт БД назовні не публікується.
  - Інтерфейс: SQL-запити, що генеруються ORM-рівнем.
- **FastAPI Server ↔ Image Storage:**
  - Інтерфейс: файлова система контейнера (Docker-том), без мережевого протоколу.
  - Формат: файли WebP і мініатюри; метадані — у PostgreSQL.

## Розгортання

Розгорнута версія: <https://baraholka-naukma.duckdns.org>. Схема (`compose.yaml`, діаграма `uml/deployment.puml`):

- **Traefik** (зовнішній reverse proxy) приймає HTTPS із сертифікатом Let's Encrypt і перенаправляє HTTP на HTTPS.
- **api** — один контейнер з FastAPI і зібраним React; файлова система лише для читання, `no-new-privileges`, запуск від непривілейованого користувача.
- **migrate** — одноразовий контейнер, що перед стартом `api` виконує `alembic upgrade head`.
- **db** — PostgreSQL 16 у внутрішній мережі `internal`, без публікації порту.
- Томи `postgres_data` і `uploads_data` зберігають дані між перезапусками; серверні сесії зберігаються в пам'яті процесу, тож після перезапуску `api` потрібен повторний вхід. Резервне копіювання: `docs/operations/backup-restore.md`.
