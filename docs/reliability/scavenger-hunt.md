## 2. Детальний опис знахідок

### REL-01: Відсутність тайм-аутів та перехоплення мережевих збоїв при роботі з Microsoft Entra ID

- **Категорія:** B — Зовнішні залежності
- **Локація:** `src/integrations/entra.py:53-82`
- **Фрагмент коду:**
  ```python
  def complete(self, flow: dict[str, Any], auth_response: dict[str, str]) -> VerifiedEntraClaims:
      try:
          result = self._get_client().acquire_token_by_auth_code_flow(flow, auth_response)
      except ValueError as exc:
          raise EntraOidcError("Невалідний state або nonce") from exc
      if "error" in result:
          raise EntraOidcError("Вхід Microsoft відхилено")
      ...
  ```
- **Чому небезпечна:** Виклики до серверів авторизації Microsoft (`login.microsoftonline.com`) виконуються бібліотекою MSAL без налаштованого явного ліміту часу (HTTP timeout). Крім того, блок `try/except` перехоплює лише `ValueError`. Будь-який мережевий збій (обрив зв'язку, недоступність DNS, 504 Gateway Timeout від Microsoft) призводить до неперехопленого винятку `requests.exceptions.RequestException`, що валить обробник FastAPI і повертає неконтрольовану 500 Internal Server Error.
- **Потенційний вплив:** Повна відмова механізму входу в систему для студентів НаУКМА, блокування воркерів під час мережевих затримок.

### REL-02: Занадто широке перехоплення винятків у роутері зображень

- **Категорія:** A — Обробка помилок
- **Локація:** `src/api/main.py:139-142`
- **Фрагмент коду:**
  ```python
  try:
      content = storage.read_image(storage_key)
  except Exception:
      raise HTTPException(status_code=status.HTTP_404_NOT_FOUND)
  ```
- **Чому небезпечна:** Перехоплюється загальний клас `Exception` без жодного логування помилки. Якщо диск пошкоджено, файлова система повернула `PermissionError`, вичерпано файлові дескриптори чи сталася помилка читання блоку, сервер маскує системну аварію під клієнтську помилку 404 (ніби фото просто не існує).
- **Потенційний вплив:** Системні збої сховища приховуються від моніторингу; адміністратори не отримують сповіщень про відмову диску.

### REL-03: Відсутність обмеження часу підключення до PostgreSQL (connect_timeout)

- **Категорія:** B — Зовнішні залежності
- **Локація:** `src/db/engine.py:37-43`
- **Фрагмент коду:**
  ```python
  _engine = create_engine(
      url,
      pool_pre_ping=True,
      pool_size=5,
      max_overflow=10,
  )
  ```
- **Чому небезпечна:** При ініціалізації з'єднання відсутній параметр `connect_args={"connect_timeout": 5}` або таймаут пулу. Якщо хост бази даних недоступний, процес підвисає на рівні стандартного системного TCP-таймауту (до 120 секунд), вичерпуючи пул робочих потоків.
- **Потенційний вплив:** Каскадне зависання всіх API-запитів застосунку при короткочасних мережевих розривах між контейнерами.

### REL-04: Нелімітована вибірка каталогу в пам'ять процесу

- **Категорія:** E — Продуктивність і блокування
- **Локація:** `src/repositories/postgres_listings.py:27-30`, `src/services/listings.py:82`
- **Фрагмент коду:**
  ```python
  def list_all(self) -> list[Listing]:
      stmt = select(ListingRow).order_by(ListingRow.created_at.desc())
      rows = self._session.execute(stmt).scalars().all()
      return [listing_row_to_domain(r) for r in rows]
  ```
- **Чому небезпечна:** Метод `list_all` вибирає всі записи таблиці оголошень без використання `LIMIT` на стороні СУБД. При зростанні бази даних завантаження тисяч сутностей у пам'ять Python блокує процесор та викликає сплески використання RAM.
- **Потенційний вплив:** Деградація часу відповіді (p99 > 3с), ризик аварійної зупинки процесу бекенда через Out-Of-Memory (OOM-killer).

### REL-05: Відсутність перевірки пробільних значень `title` і `contact` при створенні та редагуванні оголошення

- **Категорія:** C — Валідація вхідних даних
- **Локація:** `src/api/schemas/listings.py:74-80, 126-158`, `src/domain/listings.py:62-79`
- **Фрагмент коду:**
  ```python
  class ListingBase(BaseModel):
      title: str = Field(..., min_length=3, max_length=100, ...)
  ...
  class ListingCreate(ListingBase):
      contact: str = Field(..., min_length=3, max_length=200, ...)
  ...
  class ListingUpdate(BaseModel):
      title: Optional[str] = Field(None, min_length=3, max_length=100)
      contact: Optional[str] = Field(None, min_length=3, max_length=200)
  ```
- **Чому небезпечна:** Схеми `ListingCreate` та `ListingUpdate` перевіряють лише довжину сирого рядка (`min_length=3`) без попереднього `.strip()`, а ні `ListingService.create`/`update`, ні доменна сутність `Listing` (`src/domain/listings.py:62-79`) не містять захисних перевірок (`guard clauses` у `__post_init__`) на порожній після обрізання пробілів рядок. У результаті HTTP-запити `POST /api/v1/listings` та `PATCH /api/v1/listings/{listing_id}` із полями `"title": "   "` і `"contact": "   "` безперешкодно проходять межу валідації API та зберігають у базі даних невалідне оголошення.
- **Потенційний вплив:** Порушення цілісності даних каталогу (`FR-002`, `FR-003`) та зрив сценарію зв'язку з продавцем (`FR-010`): у публічному каталозі публікуються порожні картки товарів, а автентифікований покупець при відкритті контактів продавця (`GET /api/v1/listings/{id}/contact`) отримує порожній рядок `"   "`.

### REL-06: Мовчазне ковтання помилок видалення файлів без логування

- **Категорія:** D — Потенційні мовчазні збої
- **Локація:** `src/repositories/image_storage.py:449-453`
- **Фрагмент коду:**
  ```python
  def _safe_delete_blob(self, key: str) -> None:
      try:
          self._delete_blob(key)
      except (OSError, InvalidListingImageError):
          pass
  ```
- **Чому небезпечна:** Винятки дискової підсистеми ігноруються оператором `pass`. Якщо файл не вдалося видалити (блокування іншим процесом, відсутність прав доступу), система не залишає записів у логах.
- **Потенційний вплив:** Поступовий витік дискового простору через накопичення застарілих staged-файлів, неможливість діагностики проблем з файловою системою.

### REL-07: Витік пам'яті в in-memory сховищі OIDC сесій

- **Категорія:** E / D — Продуктивність та ресурси
- **Локація:** `src/services/auth_sessions.py:22-38`
- **Фрагмент коду:**
  ```python
  def save(self, state: str, flow: dict[str, Any]) -> None:
      with self._lock:
          self._flows[state] = _ExpiringValue(...)
  ```
- **Чому небезпечна:** Словник `self._flows` зберігає тимчасові параметри потоку автентифікації. Видалення запису (`pop`) відбувається лише тоді, коли користувач успішно завершив вхід. Якщо клієнти ініціюють вхід і кидають сесію, застарілі об'єкти накопичуються в пам'яті назавжди, оскільки фонове або періодичне очищення відсутнє.
- **Потенційний вплив:** Повільний витік пам'яті процесу бекенда під тривалим навантаженням.

### REL-08: Маскування системних помилок та відмов БД під клієнтський статус HTTP 422 з витоком деталей

- **Категорія:** A — Обробка помилок
- **Локація:** `src/api/routers/complaints.py:56-65`, `src/api/routers/feedback.py:45-55`
- **Фрагмент коду:**
  ```python
  def _http_error(exc: Exception) -> HTTPException:
      if isinstance(exc, (ListingNotFoundError, ComplaintNotFoundError)):
          code = status.HTTP_404_NOT_FOUND
      elif isinstance(exc, ModerationForbiddenError):
          code = status.HTTP_403_FORBIDDEN
      elif isinstance(exc, (DuplicateComplaintError, ComplaintConflictError)):
          code = status.HTTP_409_CONFLICT
      else:
          code = status.HTTP_422_UNPROCESSABLE_CONTENT
      return HTTPException(status_code=code, detail=str(exc))
  ```
- **Чому небезпечна:** Утилітарний обробник перехоплює будь-який загальний виняток `Exception` і в гілці `else:` повертає статус `HTTP 422 Unprocessable Content`. Якщо база даних PostgreSQL стає недоступною (`psycopg2.OperationalError`, розрив TCP-з'єднання, deadlock), сервер не сигналізує про внутрішню аварію (`500`/`503`), а звинувачує клієнта у валідації введених даних, одночасно виводячи системний стектрейс або деталі підключення у `detail=str(exc)`.
- **Потенційний вплив:** Спотворення метрик надійності API, дезорієнтація користувачів і клієнтського застосунку (повторні беззмістовні відправки замість очікування), витік внутрішньої інформації про інфраструктуру.

### REL-09: Витік дискового простору через накопичення застарілих файлів аватарок

- **Категорія:** E / D — Продуктивність та ресурси / Мовчазні збої
- **Локація:** `src/services/profile.py:75-85`
- **Фрагмент коду:**
  ```python
  def set_avatar(self, actor: CurrentUser, data: bytes) -> CurrentUser:
      user = self._get(actor.user_id)
      try:
          saved = self._images.save_images(
              user.user_id, [data], actor_id=user.user_id
          )
      except InvalidListingImageError as exc:
          raise InvalidProfileError(str(exc)) from exc
      user.avatar_url = saved[0].image_url
      return self._to_current(self._users.save(user), actor)
  ```
- **Чому небезпечна:** При завантаженні нової аватарки метод `set_avatar` зберігає нові зображення (`main` та `thumb`), але попередній файл, на який вказував `user.avatar_url`, не видаляється зі сховища. Оскільки аватари мають прив'язку до `user_id`, вони не є `staged`-завантаженнями та не підпадають під періодичне TTL-очищення (`cleanup_expired_staged`).
- **Потенційний вплив:** Неконтрольоване накопичення orphaned-файлів на дисковому сховищі при регулярній активності користувачів, поступове виснаження файлової системи (disk space exhaustion).

### REL-10: Порушення консистентності стану при аварії під час блокування користувача

- **Категорія:** A / D — Обробка помилок / Консистентність даних
- **Локація:** `src/services/user_moderation.py:120-134`
- **Фрагмент коду:**
  ```python
  try:
      self._users.save(user)
      self._actions.add(action)
  except Exception:
      user.is_blocked, user.block_reason, user.blocked_at = previous
      self._users.save(user)
      raise
  ```
- **Чому небезпечна:** Операція модифікації профілю користувача та фіксації аудиторської дії модератора не об'єднані в атомарну транзакцію на рівні бізнес-логіки. Якщо `_users.save(user)` пройшов успішно, а `_actions.add(action)` зазнав збою, блок `except` намагається відновити попередній стан через повторний виклик `_users.save(user)`. При транзієнтному збої БД (наприклад, розрив сесії) компенсаційна дія також падає.
- **Потенційний вплив:** Неконсистентний стан системи: обліковий запис користувача заблоковано, але аудиторський запис у журналі дій відсутній; неможливо встановити причину та автора блокування.
