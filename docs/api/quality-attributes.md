# Атрибути якості API

## Призначення

Цей документ визначає вимірювані цілі якості REST API проєкту **Baraholka NaUKMA**, умови їх провалу та способи перевірки.

Пріоритети для поточного обсягу проєкту:

1. **Безпека** — доступ до персональних даних і операцій має бути обмежений ролями та автентифікацією.
2. **Надійність** — підтверджені оголошення не повинні втрачатися після збою.
3. **Продуктивність** — каталог має залишатися швидким за очікуваного навчального навантаження.

Цілі узгоджені з нефункціональними вимогами `PERF-001`, `REL-001`, `SEC-001` і `SEC-002` у `docs/requirements/requirements.md`.

Станом на 7 жовтня 2026 року п'ять бізнес-endpoint-ів ресурсу оголошень і системний `GET /health` реалізовані та перевірені. Механізми в підрозділах «Запланована реалізація» не вважаються реалізованими, доки це не підтверджено кодом і перевіркою.

## 1. Продуктивність

### Ціль

95-й перцентиль часу відповіді endpoint-а каталогу оголошень із `limit=20` не перевищує **300 мс** при **50 одночасних користувачах**.

Додатковий критерій: частка відповідей `5xx` під час тесту не перевищує **1%**.

Це API-рівень перевірки `PERF-001`. Він є необхідною, але недостатньою умовою для початкової вимоги про завантаження всієї сторінки за 300 мс: повна сторінка окремо перевіряється наскрізним тестом разом із мережею та React-клієнтом.

### Умова провалу

Ціль вважається невиконаною, якщо під час п'ятихвилинного навантажувального тесту після хвилини прогріву виконується хоча б одна умова:

- `p95 > 300 мс`;
- частка відповідей `5xx > 1%`;
- API повертає більше 20 оголошень при `limit=20`.
- наскрізний тест сторінки каталогу перевищує 300 мс при тому самому навантаженні.

### Запланована реалізація

- пагінація каталогу з обмеженням `1 <= limit <= 100` і значенням за замовчуванням `20`;
- індекси бази даних для полів пошуку, категорії, статусу та дати публікації;
- вибірка лише необхідних полів і уникнення N+1-запитів;
- кешування публічного каталогу може бути додане після вимірювання фактичного навантаження.

### Вимірювання

- інструмент: k6, JMeter або Locust;
- сценарій: 50 одночасних користувачів запитують першу сторінку каталогу протягом 5 хвилин;
- фіксуються `p50`, `p95`, `p99`, кількість запитів і частка `5xx`;
- повна сторінка каталогу додатково перевіряється наскрізним браузерним тестом;
- результат додається до таблиці перевірок у цьому документі або до артефактів CI.

## 2. Безпека

### Цілі

1. **100%** спроб реєстрації з адресою поза доменом `@ukma.edu.ua` відхиляються контрольованою відповіддю `4xx`.
2. **0** контактних даних продавця повертається неавторизованому клієнту.
3. **100%** невалідних запитів із визначеного негативного набору отримують `400`, `401`, `403`, `404`, `409` або `422`, але не `5xx`.
4. Базове сканування OWASP ZAP не містить знахідок рівня **High**.

### Умова провалу

Ціль вважається невиконаною, якщо виконується хоча б одна умова:

- система прийняла реєстрацію з доменом, відмінним від `@ukma.edu.ua`;
- неавторизована відповідь містить `email`, Telegram або інший контакт продавця;
- хоча б один запит із негативного набору спричинив `5xx`;
- користувач змінив або зняв з публікації чуже оголошення;
- OWASP ZAP виявив хоча б одну знахідку рівня High.

### Запланована реалізація

- валідація email на рівні схеми запиту та сервісу автентифікації;
- JWT-автентифікація для захищених endpoint-ів;
- перевірка власника оголошення для операцій редагування і зняття з публікації;
- перевірка ролі `ADMIN` для модерації;
- окрема публічна схема оголошення без контактних даних;
- узгоджений формат помилок без stack trace та внутрішніх деталей;
- HTTPS у production-середовищі.

### Вимірювання

- позитивні й негативні запити через Swagger UI;
- автоматизовані інтеграційні тести доступу;
- базове активне сканування OWASP ZAP;
- ручна перевірка тіл відповідей для неавторизованих запитів.

## 3. Надійність

### Цілі

- `RPO = 0` для успішно підтверджених операцій створення оголошення;
- `RTO <= 5 хвилин` після критичного збою API або бази даних;
- жоден оброблений користувацький запит не повинен аварійно завершувати процес API.

### Умова провалу

Ціль вважається невиконаною, якщо виконується хоча б одна умова:

- після відновлення відсутнє оголошення, для якого клієнт раніше отримав успішну відповідь `201 Created`;
- працездатність системи не відновлена протягом 5 хвилин;
- невалідний користувацький запит завершує процес API;
- частково записане оголошення залишається в базі після помилки транзакції.

### Запланована реалізація

- транзакційне збереження оголошення та пов'язаних зображень у PostgreSQL;
- відкат транзакції при помилці;
- централізована обробка винятків;
- endpoint перевірки стану `/health` перед production-розгортанням;
- резервне копіювання та задокументована процедура відновлення.

### Вимірювання

- створити оголошення й отримати `201 Created`;
- примусово перезапустити API та перевірити наявність оголошення;
- провести контрольований тест відновлення PostgreSQL із вимірюванням RTO;
- перевірити rollback, штучно спричинивши помилку під час транзакції.

## 5. Аналіз компромісів

| Рішення | Покращує | Компроміс / негативний вплив | Пом'якшення |
|---|---|---|---|
| Валідація кожного запиту та JWT-перевірка | Безпеку, передбачуваність | Додає затримку й код перевірок | Прості схеми, перевикористання залежностей FastAPI, вимірювання затримки |
| Пагінація каталогу | Продуктивність і масштабованість | Для перегляду всіх даних потрібно кілька запитів | Передбачуваний `limit=20`, метадані пагінації |
| Транзакційний запис у PostgreSQL | Надійність і цілісність | Збільшує затримку запису та складність | Короткі транзакції, індекси, запис лише необхідних даних |
| Приховування деталей внутрішніх помилок | Безпеку | Ускладнює діагностику клієнтом | Кореляційний ID і детальні серверні логи без персональних даних |
| Кешування каталогу | Продуктивність | Ризик тимчасово застарілих даних | Короткий TTL та інвалідація при зміні статусу оголошення |

## 6. Перевірка валідації через Swagger UI

### Обсяг перевірки

Для **кожного** endpoint-а потрібно виконати:

1. один валідний запит;
2. запит без кожного обов'язкового параметра або поля;
3. запит із неправильним типом;
4. граничні значення числових і текстових полів;
5. запит із неіснуючим ідентифікатором;
6. для захищених операцій — без токена, з неправильним токеном і з недостатніми правами;
7. перевірку відповідності фактичного статусу та тіла OpenAPI-схемі.

### Очікувана семантика статусів

| Код | Використання |
|---:|---|
| `200 OK` | Успішне читання або оновлення з тілом відповіді |
| `201 Created` | Створено новий ресурс |
| `204 No Content` | Успішне видалення або зняття з публікації без тіла |
| `400 Bad Request` | Синтаксично або семантично некоректний запит, який не покриває схема |
| `401 Unauthorized` | Відсутня або невалідна автентифікація |
| `403 Forbidden` | Користувач автентифікований, але не має права на дію |
| `404 Not Found` | Ресурс не існує або недоступний клієнту |
| `409 Conflict` | Конфлікт із поточним станом ресурсу |
| `422 Unprocessable Content` | Вхідні дані не пройшли валідацію схеми |

### Журнал перевірок

Один endpoint може мати кілька рядків. Перевірки потрібно повторювати після кожної зміни контракту API.

| Endpoint | Сценарій | Очікуваний код | Фактичний код | Результат | Примітка / дефект |
|---|---|---:|---:|---|---|
| `GET /health` | Валідний запит через Swagger UI | `200` | `200` | ✅ | Тіло містить `status`, `app`, `version`, `timestamp`; типи відповідають OpenAPI |
| `GET /health` | Відсутні або невалідні параметри | — | — | ➖ | Endpoint не приймає вхідних параметрів |
| `POST /health` | Непідтримуваний HTTP-метод | `405` | `405` | ✅ | Додаткова перевірка поза Swagger UI |
| `GET /api/v1/listings` | Валідний запит через Swagger UI | `200` | `200` | ✅ | Контактні дані відсутні у публічній відповіді |
| `GET /api/v1/listings` | `skip=-1`, `limit=0`, `limit=101`, невалідний `category_id` | `422` | `422` | ✅ | Межі `skip >= 0`, `1 <= limit <= 100` працюють |
| `POST /api/v1/listings` | Валідне тіло через Swagger UI | `201` | `201` | ✅ | Повертається створене оголошення |
| `POST /api/v1/listings` | Відсутнє поле; короткі `title`/`description`; від'ємна ціна; невалідний UUID | `422` | `422` | ✅ | Усі невалідні тіла відхилено без `5xx` |
| `GET /api/v1/listings/{listing_id}` | Наявний ID через Swagger UI | `200` | `200` | ✅ | Контактні дані відсутні у публічній відповіді |
| `GET /api/v1/listings/{listing_id}` | Невідомий ID / невалідний UUID | `404` / `422` | `404` / `422` | ✅ | — |
| `PATCH /api/v1/listings/{listing_id}` | Валідне часткове оновлення через Swagger UI | `200` | `200` | ✅ | Оновлене значення повертається у відповіді |
| `PATCH /api/v1/listings/{listing_id}` | Короткий або `null` title; невідомий ID; невалідний UUID | `422` / `404` / `422` | `422` / `404` / `422` | ✅ | Невалідне часткове оновлення не спричиняє `500` |
| `DELETE /api/v1/listings/{listing_id}` | Видалення створеного оголошення через Swagger UI | `204` | `204` | ✅ | Тіло відповіді відсутнє |
| `DELETE /api/v1/listings/{listing_id}` | Повторне видалення / невалідний UUID | `404` / `422` | `404` / `422` | ✅ | Повторна операція обробляється передбачувано |

Додатково виконано автоматичний набір із 25 позитивних, негативних і граничних перевірок: `25 passed`, `0 failed`.

### Критерії завершення перевірки

- кожен endpoint має щонайменше один позитивний і один негативний сценарій;
- усі вхідні параметри мають типи, обмеження й описи у Swagger UI;
- невалідні користувацькі дані не спричиняють `5xx`;
- фактичні статуси та схеми відповідей відповідають OpenAPI;
- усі знайдені дефекти або виправлені, або зафіксовані як відомі обмеження.
