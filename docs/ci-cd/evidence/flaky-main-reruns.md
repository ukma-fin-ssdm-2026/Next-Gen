# Повторні запуски за період Lab 10

- **Період обов'язкової вибірки `main` (Етап 1):** 2026-10-30 — 2026-11-13 включно.
- **Додаткова перевірка PR-гілок:** 2026-11-16 — 2026-11-17 включно.
- **Джерело:** GitHub Actions REST API, поля `run_attempt`, `head_sha` і `conclusion` для запусків усіх гілок.
- **Критерій:** повторний запуск того самого workflow і SHA, який став зеленим без зміни коду.

## Результат

### Обов'язкова вибірка повторів на `main`

За командою `gh run list --branch main` зелених повторних запусків без зміни коду **не знайдено**. Єдиний запуск із `attempt > 1`:

| Workflow | SHA | Run | Спроба 1 | Спроба 2 | Висновок |
|---|---|---|---|---|---|
| `Deploy API docs` | `f933af46` | [41080526550](https://github.com/ukma-fin-ssdm-2026/Next-Gen/actions/runs/41080526550) | `failure` | `cancelled` | Не став зеленим, тому не є доказом flaky-тесту |

Команда перевірки, яку рекомендує завдання:

```bash
gh run list \
  --branch main \
  --created '2026-10-30..2026-11-13' \
  --limit 200 \
  --json databaseId,name,headSha,attempt,conclusion,createdAt,url \
  --jq '.[] | select(.attempt > 1)'
```

### Додатковий доказ із pull request

У PR-гілках знайдено **4** запуски `Performance benchmark`, які спочатку завершилися помилкою, а після ручного повтору стали зеленими на тому самому commit SHA:

| Гілка | SHA | Run | Спроби | Фінал | Висновок |
|---|---|---|---|---|---|
| `feature/frontend-new-features` | `ccb36796` | [43989008428](https://github.com/ukma-fin-ssdm-2026/Next-Gen/actions/runs/43989008428) | 1: `failure`; 2: `success` | спроба 2 | Червоний запуск став зеленим без зміни коду |
| `feat/lab10-data-analyst-and-bonus` | `b39fcb3a` | [43977054726](https://github.com/ukma-fin-ssdm-2026/Next-Gen/actions/runs/43977054726) | 1–3: `failure`; 4: `success` | спроба 4 | Три падіння, потім зелений запуск без зміни коду |
| `fix/lab09-review-feedback` | `ff833370` | [43976135299](https://github.com/ukma-fin-ssdm-2026/Next-Gen/actions/runs/43976135299) | 1–2: `failure`; 3: `success` | спроба 3 | Два падіння, потім зелений запуск без зміни коду |
| `feature/chat-api` | `2b40df51` | [43965548435](https://github.com/ukma-fin-ssdm-2026/Next-Gen/actions/runs/43965548435) | 1–2: `failure`; 3: `success` | спроба 3 | Два падіння, потім зелений запуск без зміни коду |

Ці запуски є історичним сигналом можливої нестабільності performance-перевірки або її середовища. Самі по собі вони не доводять, який конкретно тест був flaky; саме для цього бонусний workflow повторює повний набір тестів п'ять разів і порівнює JUnit-результати поіменно.

Для run [43989008428](https://github.com/ukma-fin-ssdm-2026/Next-Gen/actions/runs/43989008428) логи дають конкретний приклад нестабільного вимірювання `TP-N02 / PERF-001` на тому самому коді:

- спроба 1: `p95 = 352,35 мс`, тест упав через перевищення порога 300 мс;
- спроба 2: `p95 = 146,59 мс`, обидва performance-тести пройшли.

Отже, нестабільним виявився не функціональний результат API (в обох спробах 0% HTTP-помилок), а одноразове вимірювання затримки на спільному runner. Тест виправлено без карантину й без послаблення порога: три незалежні раунди по 50 запитів оцінюються за медіаною round p95. Один шумний раунд більше не визначає результат, але два повільні раунди з трьох усе ще валять тест. Після виправлення 10 локальних повторів benchmark пройшли стабільно.

Команда додаткової перевірки всіх гілок:

```bash
gh api --paginate \
  'repos/ukma-fin-ssdm-2026/Next-Gen/actions/runs?created=2026-11-16..2026-11-17&per_page=100' \
  --jq '.workflow_runs[] | select(.run_attempt > 1) | [.id, .name, .head_branch, .head_sha, .run_attempt, .conclusion] | @tsv'
```
