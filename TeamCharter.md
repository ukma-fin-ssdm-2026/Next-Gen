## 4. Співпраця та робочий процес

### 4.1. Стратегія гілкування (GitHub Flow)
- Основна гілка `main` містить стабільну версію проєкту, захищена від прямих пушів (`branch protection rules`).
- Робота над будь-яким завданням ведеться у власній гілці, створеній від актуального `main`.
- Злиття в `main` виконується виключно через Pull Request (PR) після проходження перевірок CI та обов'язкового Code Review.
- **Префікси гілок:**
  - `feature/...` - новий функціонал або компоненти застосунку.
  - `fix/...` - виправлення багів, помилок та невідповідностей.
  - `docs/...` - зміни та оновлення документації проєкту.
  - `ci/...` - налаштування CI/CD, пайплайнів GitHub Actions.
  - `loom-videos` - файли зі звітами та посиланнями на відео.

### 4.2. Робочий процес завдань (Issue & PR Workflow)
Повний життєвий цикл кожного завдання в репозиторії:
1. **Створення Issue:** перед початком роботи створюється завдання в GitHub Issues із зрозумілою назвою, описом мети та критеріями готовності (Acceptance Criteria).
2. **Призначення міток та виконавця:** до Issue додаються відповідні мітки типу (`type`) і пріоритету (`priority`), а також призначається відповідальний виконавець (`Assignee`).
3. **Створення гілки:** виконавець створює окрему гілку від актуального `main` з префіксом відповідно до типу завдання (наприклад, `feature/issue-12-auth`).
4. **Розробка та коміти:** зміни вносяться невеликими логічними комітами з описовими повідомленнями (наприклад, `додано компонент картки товару`).
5. **Створення Pull Request:** після завершення виконавець відкриває PR у гілку `main`, де:
   - надає короткий опис внесених змін;
   - прив'язує відповідне Issue через ключове слово (наприклад, `Closes #12`);
   - додає нотатку «Використання ШІ», якщо завдання стосується програмного коду (`.py`, `.ts` тощо, згідно з §8).
6. **Автоматична перевірка (CI):** конвеєр GitHub Actions автоматично запускає перевірки/тести. PR не може бути злитий з червоним статусом CI.
7. **Огляд коду (Code Review):** щонайменше один інший член команди переглядає зміни. Автор не має права схвалювати власний PR.
8. **Внесення правок:** усі коментарі та зауваження рев'юера мають бути обговорені та виправлені до злиття.
9. **Злиття та закриття:** після отримання схвалення (`Approve`) та проходження CI PR зливається у `main`, пов'язане Issue автоматично закривається, а робоча гілка видаляється.

### 4.3. Опис міток (Labels)
Для структурування та фільтрації завдань використовуються наступні мітки:

| Категорія | Мітка | Опис призначення |
| :--- | :--- | :--- |
| **Тип задачі** | `setup` | Налаштування репозиторію, оточення розробки, інструментів, конфігурацій та конвеєра CI. |
| | `requirements` | Завдання з аналізу, уточнення та формулювання вимог (ТЗ, User Stories, специфікації). |
| | `feature` | Розробка нової функціональності платформи (UI, API, бізнес-логіка, БД). |
| | `fix` / `bug` | Виправлення помилок, дефектів коду чи розбіжностей у поведінці компонентів. |
| | `documentation` | Створення та редагування проєктної документації, інструкцій та командного статуту. |
| **Пріоритет** | `priority:high` | Критичні або блокуючі завдання поточної лабораторної чи спринту, виконуються першочергово. |
| | `priority:medium` | Стандартні заплановані завдання поточної ітерації. |
| | `priority:low` | Другорядні завдання, оптимізації, рефакторинг або ідеї, які не блокують реліз. |

### 4.4. Означення готовності (Definition of Done - DoD)
Завдання (Issue) або Pull Request вважаються повністю виконаними та готовими до злиття в `main`, якщо дотримано таких критеріїв:
- **Відповідність вимогам:** зміст реалізованого коду або документації повністю відповідає опису та критеріям приймання в Issue.
- **Якість коду та чистота:** відсутній закоментований код, тимчасові налагоджувальні логи або невикористані імпорти/файли.
- **Успішний CI:** усі автоматичні кроки та тести у конвеєрі GitHub Actions проходять успішно (статус «зелений»).
- **Огляд коду (Code Review):** отримано щонайменше 1 схвалення (Approval) від іншого учасника команди; автор не затверджує власний PR.
- **Вирішення зауважень:** усі відкриті коментарі рев'юерів обговорені та позначені як вирішені (Resolved).
- **Відсутність конфліктів:** гілка актуалізована відносно поточного стану `main`, відсутні конфлікти злиття.
- **Нотатка «Використання ШІ»:** зафіксована згідно з §8 - наприкінці документа (для текстових файлів/артефактів на кшталт `.md`) або в описі PR (для завдань із програмним кодом `.py` тощо).
- **Зв'язок з Issue:** PR прив'язаний до відповідного завдання ключовим словом (`Closes #...`), і після злиття Issue закрито.

### 4.5. Практики роботи з вимогами (Requirements Engineering Practices)
- **Рецензування користувацьких історій (User Stories):**
  - Кожен учасник команди створює щонайменше 2 користувацькі історії у `docs/requirements/user-stories.md`.
  - Перед злиттям у `main` кожна історія обов'язково рецензується іншим учасником команди на відповідність критеріям евристики INVEST (Independent, Negotiable, Valuable, Estimable, Small, Testable).
  - Кожна історія повинна містити перевірювані критерії прийняття у формі сценаріїв або контрольних списків (формат: «Якщо..., коли..., тоді...»).
- **Перевірка нефункціональних вимог (NFR):**
  - Нефункціональні вимоги класифікуються за категоріями міжнародного стандарту ISO/IEC 25010 (продуктивність, надійність, безпека тощо).
  - Усі NFR проходять обов'язкову перевірку на вимірюваність: абстрактні описи (наприклад, «швидка відповідь») заборонені; вимога повинна містити кількісні метрики (наприклад, «час завантаження <= 300 мс при 50 одночасних користувачах», «RTO <= 5 хв»).
  - NFR проходять спільний огляд командою перед затвердженням у `docs/requirements/requirements.md`.
- **Підтримка матриці простежуваності (RTM):**
  - Будь-яка нова користувацька історія або NFR обов'язково заноситься до таблиці простежуваності `docs/requirements/rtm.md`.
  - Матриця повинна забезпечувати наскрізний зв'язок: Користувацька історія -> Тип (FR) -> Опис -> Пов'язані NFR -> Потенційні тестові випадки.

### 4.6. Управління артефактами вимог
- Усі документи вимог зберігаються виключно в репозиторії у каталозі `/docs/requirements/` (`requirements.md`, `user-stories.md`, `rtm.md`, `use-cases.md`). Зберігання вимог у сторонніх сервісах чи GitHub Wiki заборонено.
- Керівник документації підтримує головний `README.md` репозиторію в актуальному стані, забезпечуючи наявність розділу з прямими посиланнями на всі поточні артефакти вимог.

### 4.7. Архітектурні практики та управління рішеннями (ADR)
- **Архітектурні рішення (ADR - Architecture Decision Records):**
  - Ключові технічні рішення фіксуються в каталозі `docs/architecture/decisions/` у форматі `ADR-00X-<назва>.md`.
  - Кожен ADR обов'язково містить контекст проблеми, розглянуті альтернативи, критерії вибору, прийняте рішення та його наслідки (позитивні, негативні й компроміси).
  - Рішення узгоджуються командою перед фіксацією у статусі «Прийнято» (Accepted).
- **Стандарти UML-моделювання:**
  - Усі діаграми створюються сирцевим кодом у форматі PlantUML (`.puml`) та розміщуються в каталозі `docs/architecture/uml/`.
  - Діаграми компонентів, розгортання та послідовності повинні мати узгоджені назви підсистем, інтерфейсів і протоколів із текстовими описами в `high-level-design.md` та `threat-model.md`.
- **Простежуваність та якісні сценарії:**
  - Архітектура верифікується на відповідність правилу: «жодної вимоги без компонента, жодного компонента без вимоги».
  - Кожен компонент повинен брати участь у забезпеченні щонайменше однієї функціональної або якісної вимоги.
- **Управління архітектурною документацією:**
  - Усі артефакти архітектури зберігаються у каталозі `/docs/architecture/`. Керівник документації підтримує актуальність посилань у головному `README.md`.

### 4.8. Практики проєктування та реалізації API (Code-First)
- **Підхід Code-First та автогенерація специфікації:**
  - Розробка API ведеться на базі коду з декларативними типами й анотаціями (Python / FastAPI + Pydantic).
  - Специфікація OpenAPI (`/docs/api/openapi-generated.yaml`) генерується виключно автоматично з коду (жодного рядка YAML вручну). Будь-яка зміна в моделях чи ендпоінтах синхронізується в документацію через команду автогенерації або конвеєр CI.
- **Стандарти оформлення та анотування кінцевих точок:**
  - Кожен ендпоінт повинен містити зрозумілий `summary`, детальний `description`, типи параметрів шляху/запиту/тіла, приклади відповідей (`response_model`, `responses={...}`) та опис статус-кодів успіху й можливих помилок (200, 201, 400, 401, 403, 404, 422).
- **Публікація та інтерактивна документація:**
  - Інтерактивна документація надається через Swagger UI (`/docs/api/index.html`) та автоматично публікується на GitHub Pages проєкту.
- **Управління артефактами API:**
  - Код API розміщується у `/src/api/`. Документація проєктування API (`api-design.md`) та сценарії атрибутів якості (`quality-attributes.md`) розміщуються у `/docs/api/`.

### 4.9. Політика якості коду та рецензування (Code Quality & Review Policy)
- **Стандарти кодування та стилю:**
  - Обов'язкове дотримання стилю **PEP 8** для всієї кодової бази Python.
  - Детерміноване форматування коду утилітою **Black** (налаштування в `pyproject.toml`, максимальна довжина рядка — 88 символів).
  - Статичний аналіз синтаксису, стилю та відсутності невикористаних імпортів утилітою **Flake8** (налаштування у `.flake8`).
  - Обов'язкова строга типізація (**Type Annotations**) для публічних методів, моделей і функцій.
  - Наявність якісних українських рядків документації (**docstrings**) для модулів, класів та публічних інтерфейсів.
- **Інструменти статичного аналізу безпеки та аудиту:**
  - **Аналіз безпеки (Bandit):** регулярне сканування коду через `bandit -r src -ll -c pyproject.toml` згідно з настановами OWASP Secure Coding для виявлення потенційних вразливостей або небезпечних патернів.
  - **Запобігання витоку конфіденційних даних (detect-secrets):** обов'язковий pre-commit хук (`.pre-commit-config.yaml`), що блокує фіксацію ключів, токенів та паролів у системі контролю версій.
  - **Аудит сторонніх залежностей (SCA):** автоматичний моніторинг вразливостей (CVE) у зовнішніх пакетах за допомогою GitHub Dependabot (`.github/dependabot.yml`) та `pip-audit` у конвеєрі CI/CD.
- **Регламент колегіального огляду коду (Peer Code Review):**
  - Будь-який внесок розробника оформлюється виключно через окрему гілку та Pull Request у `main`. Прямі коміти в `main` заборонені.
  - Автор коду не має права самостійно затверджувати власний PR.
  - Щонайменше один інший член команди (або автоматизований агент огляду коду, наприклад Codex) проводить перевірку PR за 5 критеріями якості (стандарти кодування, безпека, архітектурні межі, документація та покриття тестами).
  - Усі відкриті зауваження та коментарі рев'юера мають бути вирішені (Resolved) до злиття.
- **Критерії готовності (Definition of Done для якості коду):**
  - Усі автоматизовані тести `pytest` виконуються успішно (100% pass rate).
  - Конвеєр GitHub Actions (`test`) має статус успішного проходження (зелений бейдж).
  - Відсутні зауваження лінтерів: 100% відповідність `black`, `flake8` та 0 вразливостей від `bandit` і `pip-audit`.
  - Згенерована специфікація OpenAPI (`docs/api/openapi-generated.yaml`) актуальна та синхронізована з кодом.
